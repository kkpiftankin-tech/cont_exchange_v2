# Открытые вопросы — F-12 Execution Hedge

1. **Архитектура: отдельный `venue_execution_adapter` сервис или слой внутри `cpp/venues/`?** Сейчас Adapter-функции (HedgeFlow state machine, child order lifecycle, normalization raw → ExecutionReport) физически живут в `cpp/venues/`. IN-005 описывает их как отдельный логический компонент `Venue Execution Adapter`. Нужно ADR (см. [ADR-012](../../../03-architecture/adr/ADR-012-venue-execution-adapter-decomposition.md)).
2. **`execution_planning` как самостоятельный сервис, или вложенный в matching?** Routing plan на основе VenueLiquidityCurve + venue.health — отдельный слой логики, который IN-005 описывает как `Execution Planning`. Сейчас интерфейс `IExecutionPlanningUseCases` объявлен в `cpp/matching/src/app/`, но не имеет реализации. См. [ADR-013](../../../03-architecture/adr/ADR-013-execution-planning-placement.md).
3. **Routing-алгоритм: proportional vs ILP vs heuristic?** IN-005 даёт формулу `qty[v] = L(v) / Sum L(v') * targetQty` как «базовый случай». Реальный production-cost-minimization может потребовать ILP (минимизация expected slippage + fees + venue.health penalty). Решение откладывается до бенчмарка. Будущая ADR при выборе.
4. **AMM-специфическая модель slippage**: для AMM (Uniswap v2/v3) slippage нелинейный (function of pool size, fee tier). Текущая `slippageBps = (avgPrice - referenceMid) / referenceMid * 10^4` корректна post-trade, но pre-trade оценка `expectedSlippage` (F12-8 проверка #3) требует венueSpecific формулы. Где живёт эта модель — в Execution Planning или в DEX/AMM adapter?
5. **Gas cost handling для DEX/AMM**: должен ли gas cost учитываться при выборе venue (как часть fee), или отдельной строкой? Сейчас `Fee` proto содержит `amount` + `currency` без указания типа (maker/taker/gas). Может потребоваться extension proto.
6. **Idempotency PostgreSQL hedgeflows**: ключ идемпотентности для `ExecutionIntent` — `(provider_id, batch_id, instrument, side)` или `client_order_id`? IN-005 §6.U8 упоминает clientOrderId как ключ, но это атрибут child_order, не HedgeFlow. Нужен составной UNIQUE.
7. **Overfill threshold value**: IN-005 даёт формулу `overfill > overfillThreshold`, но не задаёт numeric value. Часто используется 0.5% от targetQty. Параметр в `policy_config` или env?
8. **Reconciliation interval**: проверка `filledQty vs targetQty` на каждый ExecutionReport (event-driven) или периодически (например, каждые 100 ms)? Event-driven эффективнее, но требует state-machine; periodic проще, но даёт задержку.
9. **Retry urgency upgrade policy**: при timeout retry — всегда HIGH (per IN-005 §5) или зависит от gap size? Большой gap (>10% targetQty) с HIGH может дать недопустимый slippage.
10. **PreHedgeCheck RPC location**: расширить существующий `RiskService` или создать отдельный `HedgeRiskService`? Спецификация IN-005 §7.F12-8 не уточняет. Влияет на proto compatibility и client code.
11. **HedgePnL расчёт: realized vs unrealized**: формула из IN-005 §6 даёт realized PnL на момент COMPLETED. Для OPEN HedgeFlow (partial fill in progress) нужно ли вычислять unrealized PnL по текущему mid? Влияет на UI Hedge PnL Dashboard.
12. **execution.venue vs execution.reports topic conflict**: текущий repo содержит оба топика в `infra/kafka/create_topics.sh`. IN-005 канонизирует `execution.venue`. Migration plan: deprecation period, consumer cutover, retention strategy. Решение фиксируется как часть T-F12-103.
13. **Backtest parity scope**: VenueSim сейчас покрывает spot CEX. Для DEX/AMM parity требует симулятора с realistic gas/slippage. Кандидат на отдельный issue.
14. **Cancel semantics**: при cancel HedgeFlow со status=OPEN — отменять ли уже placed child orders на venues? Cascade vs leave-open. Для CEX cancel через `CancelOrder` API, для DEX уже отправленные tx нельзя отменить.
15. **Multi-leg / portfolio hedge**: текущий HedgeFlow хеджирует один symbol. Portfolio hedge (BTC + ETH с weights) — отдельная фича или extension F-12? Сейчас за пределами scope (F-09).
