## Доменные (из спеки «Незакрытое»)

### OQ-F18v2-01 — признание прибыли по факту расчёта

- **Вопрос.** Прибыль признаётся на **факте расчёта**, а не по клирингу (`realized += fq·(марка−px_факт)/1000·sgn`). В прототипе накапливается разрыв **до 6611 USD / 1200 тактов** между «прибылью по клирингу» и «прибылью по факту». Нужна явная политика: где фиксируется разрыв, куда относится (house?), допустимый порог.
- **Влияет на:** AC-F18v2-12 (A8 confirm), «Счёт дома», `INV-9`, CHK-38.
- **Статус:** `open`.
- **Адресат:** trading-domain-specialist + владелец (экономика house).

### OQ-F18v2-02 — задержка перевоза (3 такта)

- **Вопрос.** В прототипе `transfer_eta` = **3 такта** взята как константа. Обоснование величины, конфигурируемость per-route (Binance↔Kraken vs прочие), поведение при просрочке `eta` — не зафиксированы.
- **Влияет на:** AC-F18v2-17 (перевоз), `ce_transfer.eta`, `f05a_clearing_config.transfer_eta`, Э5.
- **Статус:** `open`.
- **Адресат:** data-schema-designer + trading-domain-specialist.

### OQ-F18v2-03 — выбор q при V>2

- **Вопрос.** При `V>2` площадках полос **столько же, сколько агентов** (не две константы `q_translator`/ `q_arbitrageur`). Нужна схема назначения `q_j` per-agent (формула от глубины/риска? матрица конфигов?). Текущая модель (18/30) откалибрована только для 2×2.
- **Влияет на:** AC-F18v2-09 (полосы per-kind), масштабирование `f05a_clearing_config`.
- **Статус:** `open`.
- **Адресат:** trading-domain-specialist + владелец (конфиг-политика).

### OQ-F18v2-04 — цены при пустом клиринге

- **Вопрос.** При пустом клиринге (`|S|≤C` по всем кругам, поток нулевой) множители Лагранжа `π` недоопределены сверх gauge-фиксации `π[USD@Binance]=0`. Нужна **явная политика** цен для пустого такта (нести предыдущие `π`? брать mid? помечать такт как «без цен»?).
- **Влияет на:** AC-F18v2-05 (A4/A5), альтернативный поток A-1 (пустой круг), CHK-08 (`DeadZoneNoFlow`).
- **Статус:** `open`.
- **Адресат:** trading-domain-specialist + matching (движок).

### OQ-F18v2-05 — консолидация движков клиринга (ADR-062)

- **Вопрос.** Три пути клиринга не сведены: `ce_agent_clearing` (наш), `vector_qp_solver`/OSQP (F-05A), `ContinuousClearingSolver` (Engine A/B). Нужен отдельный ADR (кандидат **ADR-062**) — какой движок канонический для такта агентов, как переиспользуется `ClearCe` / `vector_qp_pi`.
- **Влияет на:** AC-F18v2-05 (closed-form vs OSQP), размещение кода matching, T-F18-101..103.
- **Статус:** `blocking`.
- **Адресат:** solution-architect + владелец.

### OQ-F18v2-06 — party_type AGENT как архитектурное решение (ADR-063)

- **Вопрос.** AGENT — **третий** тип участника (не подтип CLIENT): дилерский инвентарь, знаковый, без резерва/неотрицательности. `CLIENT`/`HOUSE` — generated column в `accounts`; `AGENT` — отдельная таблица `ce_agent_position` (несовместимые инварианты). Требуется **ADR-063** для фиксации.
- **Влияет на:** AC-F18v2-16 (party_type AGENT), схема `accounts`/`ce_agent_position`, ledger layering.
- **Статус:** `blocking`.
- **Адресат:** solution-architect + data-schema-designer + владелец.

## Безопасность (review §11 — 2 CRITICAL)

### OQ-F18v2-07 — CRITICAL-1: нет auth-middleware на /v1/flow-orders

- **Вопрос.** `POST/GET/DELETE /v1/flow-orders` (`http_gateway.cpp:882-1010`) — **нет** auth-middleware, `user_id` берётся из тела запроса. Любой может действовать «за» произвольный `user_id`, включая будущий `__ce_house__` / `agent_id`. Строковый split CLIENT/AGENT/HOUSE в ledger защищён только строкой id → обходится с этого эндпоинта. До Э1: **починить** (gateway auth) **либо** явно принять как отслеживаемый риск с компенсирующим контролем.
- **Влияет на:** AC-F18v2-16 (изоляция AGENT/HOUSE), целостность позиций агентов.
- **Статус:** `blocking`.
- **Адресат:** security-reviewer + владелец.

### OQ-F18v2-08 — CRITICAL-2: PreHedgeCheck не в живом пути, kill-switch не останавливает

- **Вопрос.** `risk.PreHedgeCheck` **не подключён** к живому пути отправки (`cpp/venues/src/` не вызывает risk). `SetKillSwitch(halt=true)` не останавливает уже эмитированные заявки. Полоса/эмиссия v2 (A7) унаследует этот обход, как сегодняшний F-12. До Э1: включить PreHedgeCheck в путь venues **либо** принять риск явно.
- **Влияет на:** AC-F18v2-08/10 (A7 эмиссия), реюз F-12 PreHedgeCheck, безопасность kill-switch.
- **Статус:** `blocking`.
- **Адресат:** security-reviewer + владелец.

## Добавлено 2026-10-22 (EXP-2026-10-22-ce-theory-conformity)

### OQ-F18v2-10 — кому принадлежит остаток паритета (Conflict Note)

- **Вопрос.** Остаток в штуках, который возникает при клиринге цикла «покупка дешёвой копии актива, продажа дорогой» (случай B: 0,000026 BTC ≈ 1,57 USDT за круг), принадлежит связке (документ «Кривые», §7, пример 8.2) или «дому» (счёту самой биржи, CE_algorithm_v2, раздел «Счёт дома»)?
- **Влияет на:** что считать заработком арбитражёра, учёт выгод участников (блок 6 демо), ADR-068 (`house_realized_pnl` считает другое — разрыв марки и исполнения), экраны «Живые позиции» и «Система».
- **Статус:** `resolved (2026-10-22, ADR-083)`: остаток паритета принадлежит связке, «дом» — технический счёт-невязка.
- **Адресат:** владелец + trading-domain-specialist.

### OQ-F18v2-11 — физический перевод связки

- **Вопрос.** Реализовывать ли перевод актива между площадками (срок, тариф, порог $\bar Z_A$) как основное внешнее действие связки по теории. Сейчас перевода нет (`in_transit = 0`, TODO Этап 3), ноги связки закрываются рыночными заявками (`CE_ARB_MARKET_HEDGE=1`), что по расчёту простейшего случая либо уничтожает арбитраж, либо удваивает оборот.
- **Влияет на:** ADR-065 Q2, ADR-069, ADR-073, ADR-080; контракт `RegisterTransfer`; OQ-F18v2-02 (задержка перевоза).
- **Статус:** `resolved` ([ADR-084](../../../03-architecture/adr/ADR-084-ce-link-physical-transfer.md), 2026-10-22): перевод — целевое действие связки; порог по накопленному перекосу с учётом платы за перевод, срок 3 такта (настраивается), тариф 0, на dev перевод смоделирован в ledger (`ApplyNodeTransfer`). Остаётся открытым: калибровка порога по дисперсии базиса (Γ_A), постоянный учёт переводов, ведомость остатка паритета. **Адресат:** владелец + solution-architect.

### OQ-F18v2-12 — верификация коэффициента конвертации $\kappa$ связки и калибровка новых пределов глубины

- **Вопрос.** (1) Связка котирует жёсткий паритет копий актива; коэффициент $\kappa$ в базовом документе берётся из реестра активов, но реестра в коде нет (у всех связок $\kappa=1$). Нужен ли реестр с проверкой «квантиль 95 % разности $|\ln(P_A/(\kappa P_B))|$ за окно не выше допуска» и закрытием связки при дрейфе (страница v6, патч 6; [F-05A] §4.10.4: неизвестная конвертация — fail-closed)? (2) Какие значения $W_T$ и $\gamma$ задавать капитальному пределу (ADR-085), какой режим уценки включать (LINEAR или DISP) и с каким пределом возраста? (3) Нужна ли глубина связки $\alpha_A=W_A/(\gamma_A\varsigma^2_{tr}\tau_{tr})$ вместо констант `CE_TRANSFER_ALPHA_*` (нет входных данных: капитал связки, дисперсия базиса за время перевода)?
- **Влияет на:** ADR-085, ADR-069, ADR-084, CALC-CE-TRANSLATOR-DEPTH; реестр активов (отсутствует).
- **Статус:** `open`. Для (2) в ADR-085 даны тактовые глубины стенда как ориентир. **Адресат:** владелец + solution-architect.

### OQ-F18v2-16 — баланс «ловить реальные возможности» против «не давать ложных сигналов»

- **Вопрос.** Пока рыночные данные между биржами не синхронизированы,
  защитный запас на возраст котировок — единственный способ отсечь
  фантомные арбитражные сигналы, но он режет по живому: без запаса система
  ловит ≈42% реальных возможностей ценой того, что 3 из 4 сигналов ложные;
  с запасом — почти не торгует, но и почти не ошибается (текущий выбор).
  Какой баланс приемлем на время, пока данные не станут синхронными?
- **Влияет на:** частоту срабатывания хеджа, объём торговли, ADR-075.
- **Статус:** `open`.
- **Адресат:** владелец + trading-domain-specialist.
- **Источник:** [EXP-2026-10-14-clearing-diagnosis](../../../../docs/experiments/EXP-2026-10-14-clearing-diagnosis.md).

### OQ-F18v2-19 — возвращать ли арбитражёра к модели «только перевозка, без выхода на рынок»

- **Вопрос.** Честная (без заглядывания в прошлое) проверка показала, что

  отмены недавно принятого решения дать ему рыночный выход? Тесно связано с
  OQ-F18v2-11 (физический перевод связки) — если перевод станет основным
  действием арбитражёра, вопрос о рыночном выходе может закрыться сам собой.
- **Влияет на:** ADR-073, ADR-080, риск отдельных агентов-арбитражёров.
- **Статус:** `open`.
- **Адресат:** владелец.
- **Источник:** [EXP-2026-10-22-arbitrageur-pnl](../../../../docs/experiments/EXP-2026-10-22-arbitrageur-pnl.md),

### OQ-F18v2-21 — делать ли честный симулятор исполнения режимом по умолчанию

- **Вопрос.** Симулятор сейчас может сматчить заявку со сделками, которые

### OQ-F18v2-22 — физический перевод остаётся единственным путём вперёд для прибыльности арбитражёра

- **Вопрос.** Числовой пример на реальных ценах показывает: «правильное»
  (с теоретически верными знаками) закрытие позиции арбитражёра на рынке
  полностью обнуляет весь арбитражный доход в системе — переводчик и
  арбитражёр просто гасят прибыль друг друга. Это подтверждает, что без
  физического перевода роль арбитражёра **не может в принципе** быть
  самостоятельно прибыльной тем способом, что заложен сейчас — то есть
  единственный путь вперёд — реализовать перевод (OQ-F18v2-11), а не
  донастраивать параметры текущего рыночного механизма. Согласен ли
  владелец с этим выводом как основанием для приоритизации OQ-F18v2-11?
- **Влияет на:** приоритет реализации физического перевода (OQ-F18v2-11),
  ADR-073, ADR-080.
- **Статус:** `open`.
- **Адресат:** владелец + trading-domain-specialist.
- **Источник:** [EXP-2026-10-22-ce-theory-conformity](../../../../docs/experiments/EXP-2026-10-22-ce-theory-conformity.md).

### OQ-F18v2-23 — допустимая погрешность цены для порогов свежести данных

- **Вопрос.** Оба порога устаревания котировок (мягкий — для частоты

- **Статус:** `open`.
- **Адресат:** владелец + trading-domain-specialist.
- **Источник:** [EXP-2026-10-15-data-validity](../../../../docs/experiments/EXP-2026-10-15-data-validity.md).

### OQ-F18v2-24 — завышенная оценка волатильности из объединённого потока бирж

- **Вопрос.** Оценка волатильности, используемая и для защитного запаса по
  возрасту данных, и для порога срабатывания хеджа, считается по
  объединённому потоку котировок всех бирж сразу, из-за чего обычная
  межбиржевая разница цен попадает в неё как будто это волатильность —
  завышение до 2,9× по дисперсии при частом опросе. Это означает, что
  система сейчас торгует осторожнее, чем могла бы при честной оценке.
  Приемлемо ли оставить это как временный запас прочности, или нужно
  приоритизировать замену способа оценки?
- **Влияет на:** ADR-075 (`CE_AGE_DEAD_ZONE_K`), ADR-066
  (Γ=γσ²τ, `ce_asset_volatility`), частоту и агрессивность хеджа.
- **Статус:** `open`.
- **Адресат:** владелец + trading-domain-specialist.
- **Источник:** [EXP-2026-10-15-data-validity](../../../../docs/experiments/EXP-2026-10-15-data-validity.md).
