# ADR-030: Legacy MVP migration policy

## Контекст

В репозитории присутствует `legacy_mvp/` — справочный исходный MVP. CLAUDE.md
§23 уже задаёт правила, но как ADR это не закреплено, из-за чего возможна
путаница: считать ли legacy источником истины или целевой кодовой базой.

## Решение

Зафиксировать политику работы с legacy:

- **`legacy_mvp/` — read-only reference**, кроме явных migration-задач.
- **Не источник истины**: при конфликте с `docs/` или `contracts/proto/`
  приоритет у docs/contracts (CLAUDE.md §3.1).
- **Никаких новых production-фич** в `legacy_mvp/`.
- **Mapping** legacy-сервис → целевой C++ компонент оформляется в
  migration-доке перед переносом.
- **Тесты до замены**: поведение, переносимое из legacy, покрывается тестами
  до удаления/замены legacy-логики.
- Перенос кода оформляется как отдельный refactoring/migration task, не
  смешивается с новым skeleton без плана.

## Альтернативы

- **Удалить `legacy_mvp/`** — отклонено: ценный справочник идей, UI assets, DB diagrams, прежних паттернов.
- **Развивать legacy как продакшн** — отклонено: архитектура расходится с новым docs-as-code skeleton.

## Последствия

- **Плюс:** ясный статус legacy; нет случайного дрейфа истины в legacy.
- **Минус:** дублирование части идей до завершения миграции.

## Обратимость

Высокая. Политика; не затрагивает рантайм нового skeleton.
