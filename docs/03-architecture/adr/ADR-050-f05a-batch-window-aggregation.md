# ADR-050 — F-05A batch-window aggregation (cross-venue / triangular)

> **Проблема:** сейчас векторный клиринг F-05A триггерится **поканально** — на
> каждую входящую `VenueLiquidityCurve` (одна биржа + одна пара). Поэтому каждый
> batch имеет asset-basis из 2 активов, `Wx=0` сводит лишь bid/ask одной биржи →
> арбитража нет, `x≈0` **на всех данных**. Это противоречит постановке IN-014,
> где клиринг обязан агрегировать уровни **многих бирж и многих пар** в **один**
> `VectorClearingInput` над **общим** `AssetBasis` (кросс-venue и треугольный
> арбитраж).

## Контекст

Постановка (IN-014) и производные доки требуют агрегированный клиринг:

- **IN-014 §12.1** отвергает поканальный клиринг: «Обычный matching по каждой паре
  отдельно не видит, что ликвидность может клириться через цикл активов
  `BTC → USD → ETH → BTC`… Три разных внешних ордера (BTC/USD ask, BTC/ETH bid,
  ETH/USD bid) образуют самобалансирующуюся комбинацию».
- **IN-014 §12.3**: «unified solver вместо отдельных pair books… основа для
  arbitrage-free venue aggregation».
- **AC-F05A-006**: треугольный `BTC/USD + BTC/ETH + ETH/USD` клирится в `Wx=0` —
  три пары в одном базисе `[BTC, ETH, USDT]`.
- **R-F05A-002 / R-F05A-004**: каждый external level — отдельный столбец `W`; клиринг —
  единый asset-balance `Wx=0` над всем `W` (не по кривой).
- **UC-F05A-01** («Venue Liquidity Builder») уже описывает нужный триггер:
  «поступление нового VenueSnapshot / нормализованного набора внешних order levels
  **или тик batch-таймера market_data**», с общим детерминированным asset-basis и
  staleness-фильтром (KI-F05A-004).
- Контракт `VectorClearingInput { batch_id; AssetBasis basis; repeated VectorFlowSegment segments }`
  и `VectorFlowSegment.{venue_id, pair}` рассчитаны на сегменты из **разных** венью/пар
  в одном входе.

Текущая реализация ([`cpp/market_data/src/app/market_data_uc.cpp`](../../../cpp/market_data/src/app/market_data_uc.cpp),
`OnLiquidityCurve`) векторизует и публикует **каждую кривую отдельно**
(`batch_id = snapshot_id | curve_id | venue|symbol`). Batch-таймер / snapshot builder
из UC-F05A-01 **не реализован** — отсюда single-venue/single-pair батчи и `x≈0`.

## Решение

Ввести **оконный snapshot builder** в `market_data` (реализация UC-F05A-01):

1. **Буфер свежих кривых.** Держать «последнюю кривую на ключ `(venue_id, pair)`».
   Каждое сообщение `venue.liquidity.fob` обновляет буфер, но **не** триггерит
   немедленную публикацию.
2. **Batch-таймер.** По тику окна (интервал `F05A_BATCH_WINDOW_MS`, dev-default
   1000 ms) собрать **один** снапшот из всех **свежих** записей буфера.
3. **Скоуп — глобальный.** Окно агрегирует **все** свежие `(venue, pair)` из
   буфера (без привязки к Sim-сессиям); фактический скоуп задаётся только
   freshness-порогом. Sim-скоуп (F-20) — возможное будущее сужение, не сейчас.
4. **Freshness-модель staleness** (KI-F05A-004, «venue freshness score»):
   - Буфер держит **только последнюю** кривую на `(venue_id, pair)` — новая
     вытесняет старую («старый снапшот исчезает, как только пришёл новый»).
   - Каждой буферизованной кривой присваивается **вес свежести**
     `f = clamp(1 − age/F05A_STALE_LEVEL_MS, 0, 1)`, убывающий с возрастом
     (`age = window_close − curve.event_ts`); можно домножать на `curve.confidence`.
   - Вес применяется к **ёмкости сегмента**: `q_max_eff = q_max · f` (устаревшая
     ликвидность даёт меньше исполняемого объёма; при `f→0` сегмент не участвует).
   - **Жёсткий порог:** `age ≥ F05A_STALE_LEVEL_MS` (`f=0`) → уровень **отбрасывается**;
     метрика `stale_external_levels_total`. Пустое окно → снапшот не публикуется.
5. **Общий AssetBasis.** `BuildAssetBasis` по объединению `base+quote` **всех**
   свежих пар (отсортированное объединение) → единый индекс активов, в котором
   выражаются `w_i` сегментов всех венью/пар. Это делает кросс-venue и треугольный
   арбитраж представимым.
6. **Сборка `W`.** Каждый уровень каждой свежей кривой → отдельный столбец `w_i`
   (R-F05A-002), сегмент несёт `venue_id` + `pair`. Публикуется **один**
   `VectorizedLiquiditySnapshot` на окно.
7. **`batch_id` окна.** Детерминированный id окна (например `w|<window_close_ms>|<scope_hash>`),
   а НЕ `snapshot_id`/`curve_id`/`venue|symbol`. Один `batch_id` = один агрегированный
   клиринг.
8. **Детерминированный порядок сегментов** (F-15 replay, NFR-F05A-001, AC-F05A-010):
   стабильная сортировка `(venue_id, pair, side, k)`; индекс позиции = **`seg_index`**,
   который persist'ится (столбец `vector_flow_segments_history.seg_index`) — чтобы
   `x[i] ↔ segment[i]` восстанавливалось точно при мульти-venue (текущая
   реконструкция по `source_order_id` верна только для single-venue).

Границы окна в **replay** воспроизводятся из event-timestamp'ов кривых (а не
wall-clock), чтобы `W, x, pi, residual` были бит-в-бит детерминированы (AC-F05A-010).

Раскатка за флагом **`F05A_BATCH_WINDOW_ENABLED`** (default off на первом шаге):
off → прежнее поканальное поведение; on → оконный агрегатор. Это делает изменение
обратимым и позволяет сравнить x/арбитраж side-by-side.

## Альтернативы

- **(A) Поканально (текущее).** Отвергнуто: single-venue/single-pair, `x≈0`,
  противоречит IN-014 §12.1/§12.3, R-F05A-002/004, AC-F05A-006.
- **(B) Event-driven агрегатор** (пересобирать снапшот на каждую кривую, debounce
  публикацию). Отвергнуто как основной режим: недетерминированные границы для
  replay F-15; таймерное окно детерминируемо по event-времени.
- **(C) Агрегация на стороне matching** (matching буферизует `marketdata.vectorized`).
  Отвергнуто: UC-F05A-01 закрепляет роль builder за market_data; matching остаётся
  stateless per-event (проще для replay и границ сервисов §10.3).

## Последствия

**Положительные**
- Кросс-venue и треугольный арбитраж становятся представимыми → ненулевые `x`,
  реальные хедж-черновики (F-12), осмысленные `pi`/клиринговые курсы.
- Соответствие постановке (IN-014 §12, UC-F05A-01, AC-F05A-006).

**Требуют внимания**
- **Семантика `batch_id`** меняется (оконный, мульти-venue). Downstream уже
  ключуется по `batch_id` (`vector_clearing_results`, `vector_flow_segments_history`,
  detail-UI) — ломающих изменений схемы нет, но detail-view должен перейти с
  реконструкции порядка по `source_order_id` на **`seg_index`**.
- **Новый столбец** `vector_flow_segments_history.seg_index UInt32` (ALTER ADD,
  default 0 для старых строк).
- **Freshness/staleness** определяет состав окна; нужны метрики и порог.
- **Детерминизм** окна для F-15 — обязателен (границы по event-времени).
- **Нагрузка**: один солв на окно вместо N солвов на N кривых — как правило дешевле.

## Обратимость

Высокая. За флагом `F05A_BATCH_WINDOW_ENABLED` (default off) — мгновенный откат к
поканальному режиму. `F05A_BATCH_WINDOW_MS` / `F05A_STALE_LEVEL_MS` — тюнятся env.
Единственное необратимое — добавление колонки `seg_index` (аддитивно, безопасно).

## Решения владельца (2026-08-28)

1. **Окно** — фиксированный интервал (`F05A_BATCH_WINDOW_MS`, dev-default 1000 ms);
   границы детерминированы по event-времени для replay F-15.
2. **Скоуп** — **глобальный**: агрегируются все свежие `(venue, pair)`; фактический
   скоуп задаётся только freshness-порогом (Sim-скоуп — возможное будущее сужение).
3. **Staleness** — буфер держит только последний снапшот на `(venue, pair)` (новый
   вытесняет старый); **вес свежести** `f = clamp(1 − age/F05A_STALE_LEVEL_MS,0,1)`
   применяется к `q_max` (устаревшая ликвидность вносит меньше объёма); при
   `age ≥ F05A_STALE_LEVEL_MS` уровень отбрасывается. Порог dev-default 2000 ms.
