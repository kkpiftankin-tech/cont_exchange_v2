# ADR-053 — Safe-translator модель ликвидности венью

> **Решение владельца (2026-09-07):** кривая ликвидности венью, которая идёт в
> клиринг, считается по алгоритму «безопасного переводчика» из
> `orderbook_liquidity_architecture_separate_charts.py`:
> из VWAP-нормализованной накопительной глубины стакана берётся тончайшая
> сторона/уровень `α_ext = min_k D_k/|δ_k|`, применяется safe-share haircut
> `α_T = θ·α_ext` (θ=0.60), и наклон сегмента калибруется по `α_T`.
> Клиринг остаётся в **log-ценах** (треугольная согласованность курсов).

## Контекст

F-05A клирит внешнюю ликвидность как QP `min ½xᵀPx + qᵀx s.t. Wx=0, x∈[q_min,q_max]`
(ADR-048/052). Один двусторонний сегмент на `(venue, pair)` (ADR-052): якорь `a`,
наклон `m` (`P=diag(m)`), знаковый `x` (покупка `x>0` / продажа `x<0`).

До этого ADR (code-only «ADR-053: log-цены»):

- якорь `a = log(mid)`; курс quote/base = `exp(π_quote − π_base)` — треугольник
  согласован (`ETH/USDT = ETH/BTC × BTC/USDT`);
- наклон `m = ½(bid_slope + ask_slope)`, где каждая сторона =
  `|Δlog(p)| / q` по **крайним** точкам FOB-кривой (best и worst `p_of_q`).

Проблемы прежнего наклона:

1. **Endpoint-оценка** — учитывает только первую и последнюю точку, игнорирует
   форму глубины (VWAP) между ними.
2. **Нет risk-haircut** — переводчик обещает CE полную внешнюю ликвидность, хотя
   исполнить её безопасно можно лишь частично (проскальзывание, latency, доля
   рынка). Это завышает уверенность клиринга.
3. **Расхождение с UI** — график ликвидности (F-05A ops-страница) строил кривую
   по сырому стакану + VWAP, а движок клирил по endpoint-log-наклону: картинка
   ≠ то, что клирится.

Прикреплённый скрипт формализует «кривую безопасного переводчика на CE»:
raw cumulative book → normalized VWAP book → `α_ext` → θ-haircut → линейный `β_T`.

## Решение

**Единая модель наклона (safe-translator), клиринг в log-ценах.**

Для каждой стороны кривой (bid, ask), по накопительным уровням `k`:

$$
Q_k=\sum_{i\le k} v_i,\quad D_k=\sum_{i\le k} p_i v_i,\quad
P^{VWAP}_k=\frac{D_k}{Q_k},\quad
\delta_k = 10^{4}\,\Bigl|\ln\frac{P^{VWAP}_k}{\text{mid}}\Bigr|.
$$

Тончайшая ликвидность по **обеим** сторонам и haircut:

$$
\alpha_{ext}=\min_k \frac{D_k}{\delta_k},\qquad
\alpha_T=\theta\,\psi_{age}\,\psi_{conf}\,\alpha_{ext},\qquad \theta=0.60.
$$

Наклон сегмента (клиринг в log-ценах, ADR-052/053 сохраняется):

$$
m=\frac{\text{mid}}{10^{4}\,\alpha_T},\qquad a=\ln(\text{mid}).
$$

Эквивалентная **линейная** «safe-translator» кривая (для отображения и как
диагностика) — та, что рисует скрипт:

$$
\beta_T=\frac{\text{mid}^2}{10^{4}\,\alpha_T}=\text{mid}\cdot m,\qquad
P(q)=\text{mid}+\beta_T q.
$$

Связь `β_T = mid·m` означает: log-наклон `m` и линейный `β_T` совпадают **в
первом порядке** у якоря (`dP/dq = P·d(ln P)/dq = mid·m`). Поэтому safe-translator
и log-клиринг согласованы у mid, а log-форма даёт треугольную согласованность.

Движок эмиттит в контракт сегмента диагностику `α_ext, α_T, β_T, θ` — чтобы UI
показывал **ровно то, что клирится** (единый источник истины формулы).

**Источник кривой (решение владельца 2026-09-07):** safe-translator считается из
**СЫРОГО стакана венью** (`venue_snapshots`, `bid_prices/ask_prices/*_quantities`),
как в исходном скрипте, а НЕ из FOB-кривой (`venue.liquidity.fob`). `market_data`
уже держит последние сырые снапшоты (consumer `venue.snapshots`); `FlushVectorWindow`
берёт их копию (thread-safe) и считает `mid, α_ext, Q_bid, Q_ask` из сырых уровней.
Так движок и дисплей совпадают (оба из сырого стакана), без двойного haircut поверх
FOB-деградации. Тег сегмента `translator_model`: `safe_vwap_raw` (сырой) /
`safe_vwap_fob` (fallback, если сырого нет) / `log_endpoint`.

**Конфиг (обратимость):**

- `F05A_TRANSLATOR_MODEL = safe_vwap` (новая, по умолчанию) | `log_endpoint`
  (прежняя ADR-052/053-code) — флаг в `market_data`.
- `F05A_TRANSLATOR_SOURCE = raw` (сырой стакан, по умолчанию) | `fob` (FOB-кривая).
- `F05A_SAFE_SHARE = 0.60` — θ. `ψ_age/ψ_conf` — хуки (по умолчанию 1),
  зарезервированы под свежесть/уверенность снапшота.

## Альтернативы

1. **Полностью линейный клиринг** (`a = mid`, наклон `β_T`, без log). Отклонено:
   ломает треугольную согласованность курсов (ADR-053-log), ради которой log и
   вводился; кросс-пары (ETH/BTC) рассогласуются.
2. **Оставить endpoint-log-наклон** (прежняя формула). Отклонено: игнорирует
   форму глубины (VWAP) и не имеет risk-haircut → завышенная уверенность.
3. **Haircut только на фронте** (визуально). Отклонено: клиринг всё равно считал
   бы по завышенной ликвидности; расхождение UI↔движок сохраняется.

## Последствия

- **Клиринговые цены π меняются**: с `θ<1` наклон растёт (`m ∝ 1/α_T`) → кривая
  «жёстче» → меньше объёма исполняется по краю диапазона; клиринг консервативнее
  и безопаснее для переводчика.
- **UI и движок совпадают**: оба используют формулу этого ADR (`α_ext, α_T, β_T`).
- **Новые поля контракта** `VectorFlowSegment` (диагностика) — additive,
  consumers не ломаются (см. `docs/06-api/messaging/venue-liquidity-fob.md`).
- **Тесты**: `vectorize_test` проверяет `m = mid/(10⁴·α_T)`; conservation `Wx=0`
  не меняется (меняется только диагональ `P`).
- Прежняя формула доступна флагом `F05A_TRANSLATOR_MODEL=log_endpoint`.

## Обратимость

**Высокая.** Переключение модели — env-флаг `F05A_TRANSLATOR_MODEL`; прежний
endpoint-путь сохранён. Контрактные поля additive (можно игнорировать). Откат —
без миграции данных.
