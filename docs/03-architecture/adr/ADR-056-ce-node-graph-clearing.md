# ADR-056 — Граф узлов CE и снятие жёсткого Wx=0

> **Решение владельца (2026-09-10, `CE_algorithm_spec.md` §1,3; `CE_virtual_counterparties.md` §3,7).**
> Единица клиринга — **узел «валюта@площадка»** (`BTC@Binance`, `USDT@OKX`), а не актив.
> Баланс `Wx=0` требуется **только по узлам площадок**; узлы собственной книги
> (`asset@__book__`) из ограничений исключены и несут цену-марку `μ` в линейном члене.
> Это снимает «позиция биржи запрещена по построению».

## Контекст

Сейчас клиринг F-05A строит базис из активов (`BuildAssetBasis`,
[vectorize.hpp](../../../cpp/market_data/src/domain/vectorize.hpp)) и задаёт `Wx=0`
жёстким равенством `l=u=0` по всем строкам ([vector_qp_solver.cpp:56-58](../../../cpp/matching/src/domain/vector_qp_solver.cpp#L56-L58)).
Следствие (`CE_virtual_counterparties.md` §7, проверено): `Σ_j f(quote a@j) ≡ 0`, то есть
изменение позиции биржи тождественно ноль. Позиция может появиться только если у
переводчика есть **собственный остаток на площадке** (STOCK-плечо, ADR-055), а он требует
свободного узла книги — чего жёсткий `Wx=0` не допускает.

Кроме того, биткойн на Binance и на Kraken — разные веши (перевод стоит денег и времени),
поэтому базис активов теряет географию ликвидности, а арбитраж «находится» там, где его
нет.

## Решение

- **Базис узлов** `BuildNodeBasis`: узлы `asset@venue` + по одному `asset@__book__` на
  актив; порядок стабильный (сортировка по строке-ключу). Формат ключа `"ASSET@VENUE"`
  фиксируется в ADR (чтобы BFF мог парсить). `AssetBasis.Entry.asset` наполняется
  `"BTC@Binance"` (контракт аддитивен).
- **Матрица `W`**: строка на каждый **балансируемый** узел (только площадки), столбец на
  сегмент. Узлы книги строк не получают → свобода позиции.
- **Цена узла книги** входит в линейный член как марка
  `μ_a = Σ_j α_j·m_{a,j} / Σ_j α_j` (средневзвешенный по глубине mid). Марка — **вход**, не
  выход; её ошибка даёт систематический дрейф позиции (диагностический сигнал, ADR-057).
- **Снятие Wx=0 (Ш-2):** по узловым строкам `l=−q_запас`, `u=+q_запас` (box запаса), с
  квадратичной ценой использования запаса; узлы площадок остаются `l=u=0`.
- **`pi` = цены узлов** (дуальные строк `W`); уже присутствует в
  [VectorClearingResult.pi](../../../cpp/matching/src/domain/vector_qp_solver.hpp#L117)
  (вопреки анализу источника — см. Conflict Note).

**Реализация:** `market_data` (`BuildNodeBasis`, сегменты по рёбрам узлов) + `matching`.

**Поправка (2026-09-10, Срез 1):** CE-клиринг реализован как **отдельный выпуклый
Newton-движок** [`domain/ce_agent_clearing.hpp`](../../../cpp/matching/src/domain/ce_agent_clearing.hpp)
(минимизация `Φ(x)=Σ½α((|d|−c)₊)²` active-set Newton'ом; узлы книги свободны, узлы площадок
балансируются), а не через OSQP-ветку `AssembleProblem`. Причина: движок доказанно
воспроизводит Python-эталон до 1e-6 без внешних зависимостей и без риска рассинхрона с
academic-формой ADR-052. **OSQP (`vector_qp_solver`) остаётся для F1/two-sided путей** (ADR-048/052)
без изменений. Математически эквивалентно box-формулировке; отличается лишь движок.

## Conflict Note (источник vs код)

Источник (`CE_algorithm_spec.md` Р-5/Р-7, §13) утверждает, что `matching` не собирается и
`solve.pi` отсутствует. На HEAD `1e8bf6f` это **неверно**: `pi` есть
(vector_qp_solver.hpp:117), конструктор 5-арг с `two_sided` (139-143), `matching` собран,
`ce.position.delta` работает e2e. В коде правится только базис и снятие `Wx=0`, а не
«5 ошибок компиляции».

## Альтернативы

- **Базис активов + мягкий surplus (ADR-047)** — не даёт узловой географии и STOCK;
  отвергнуто.
- **Отдельный «казначейский» солвер поверх клиринга** — двойной проход, рассинхрон; хуже
  единого QP по узлам.

## Последствия

- `vector_liquidity.proto`: `NodeBasis`/формат ключа; сегмент += `agent_id`; QP-сборка
  меняется (ADR-048 дополнен).
- Позиция биржи становится наблюдаемой величиной (вход в ADR-057), а не нулём.
- `p*`/цены узлов — из дуальных; UI матрица «валюта×площадка» + строка марки.

## Обратимость

За флагом: при выключении — базис активов и жёсткий `Wx=0` (ADR-052/048), позиция ≡ 0.
`NodeBasis`/`agent_id` аддитивны. Эталон — Python `agents_vc.py` (совпадение до 1e-9).

## Conflict Notes (F-18 v2, 2026-09-15)

> Ревизия по [`CE_algorithm_v2.md`](../../../incoming-docs/2026-09-15-CE_algorithm_v2.md).
> См. [ADR-061](ADR-061-ce-v2-agent-position-band-hedge.md) (`proposed`). Тело ADR-056 не
> переписывается; `status` остаётся `accepted`, во `related` добавляется ADR-061.

**Узел книги / марка `μ` убраны; вместо них — house-столбец.** Текущее решение вводит по
одному свободному узлу `asset@__book__` на актив с боксовой релаксацией `Wf=0`, чтобы дать
STOCK-плечу разрядку. Поскольку STOCK убран (ревизия [ADR-055](ADR-055-ce-virtual-counterparties-agents.md)),
механизм свободного узла на актив избыточен: v2 заменяет его **одним** столбцом «счёт дома»
в узле **нумерария**.

- `BuildNodeBasis` v2: узлы — **только** `asset@venue` (per-asset `asset@__book__`
  убираются). Строгое равенство `Wf=0` возвращается по **всем** узлам площадок (боксовая
  релаксация book-строк отменяется).
- Ранг/фиксируемость восстанавливает **единственный** house-столбец — единичный вектор в
  узле нумерария (не по одному на актив); это переменная-невязка, а не агент (без
  якоря/наклона/полки/полосы, заявок не порождает). Забирает арб-прибыль `= разница цен`.
- Марка `μ` как вход линейного члена book-узла больше не нужна; house-цена фиксируется той
  же конвенцией пиннинга нумерария (`π[USD@Binance] = 0`).
- **Именование ключа** — отдельный зарезервированный псевдо-узел (например
  `HOUSE@<numeraire_venue>`), **не** переиспользование суффикса `@__book__`, чтобы не ломать
  существующих парсеров формата `"ASSET@VENUE"` (BFF/фронт).
- **Обратимость:** средне — пересборка `BuildNodeBasis`/QP-сборки за флагом `CE_V2_GRAPH`
  (default OFF); при зарезервированном ключе (не `@__book__`) переход по формату
  аддитивно-совместим.
