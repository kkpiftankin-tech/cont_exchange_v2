# ADR-057 — Трёхуровневая позиция CE

> **Решение владельца (2026-09-10, `CE_algorithm_spec.md` §1.3; `CE_virtual_counterparties.md` §6,11).**
> Позиция ведётся на **трёх уровнях**: агент (`committed`/`filled`), узел
> (`qty`/`target`/`in_transit` по `asset@venue`), актив
> (`Z_a = Σ_venue qty + in_transit + committed − target`). Каждое из трёх решений
> (куда/сколько, можно ли, насколько допустимо) читает своё число.

## Контекст

ADR-054 ввёл NOP биржи (`nop = assets − client_liability`) и хедж по агрегату. Но
(`CE_virtual_counterparties.md` §6): «одно число для трёх разных решений» — источник
ошибок. Куда и сколько исполнять знает **поток агента** (в нём зашит адрес площадки);
исполнима ли нога — знает **остаток узла** `Q_{a,j}` (нельзя продать на OKX биткойн,
лежащий на Kraken); насколько допустим риск — знает **агрегат** `Z_a`. Текущий
`risk_uc` (`nop = assets − client`) не различает узлов, не вычитает цель и не учитывает
«в пути»/«отправлено», из-за чего первый же тик при `CE_CAPITAL_SEED_BTC=10`, θ=0.25 даёт
`SELL 10 BTC` — продажу всего капитала (§A8 Р-13).

## Решение

- **Уровень агента** `agent_id`: `committed`, `assigned_last`, `filled_cum` (ADR-058).
- **Уровень узла** `asset@venue`: `qty` (факт), `target` `Q*`, `in_transit_in`. Меняется
  **только подтверждениями** извне (`execution.reports`), не решением клиринга.
- **Уровень актива** `asset`:

      Z_a = Σ_venue qty_{a,venue} + in_transit_a + committed_a − Σ target_a

  плюс `limit`, марка `μ_a`, накопленный дрейф. `Z_a` — ценовой риск, не зависящий от
  того, на какой площадке актив лежит.
- **Агрегатный лимит** — **единственный** вход агрегата в клиринг (`CE_algorithm_spec.md`
  §A2): при `|Z_a|>Z_limit` к скоростям плеч добавляется `−ρ_lim·(Z_a − sign·Z_limit)`.
- **NOP — частный случай.** Без клиентов и без плеча запаса `Σ_j f(quote a@j)≡0` ⇒ `Z_a`
  сводится к прежнему NOP; метрика ADR-054 остаётся корректной как измерение инварианта.
  Формула универсальна: `Z_a` ⊇ NOP.

**Реализация:** `ledger` хранит остатки с ключом `(account, asset, venue)`, новый RPC
`GetNodeBalances`; `ApplyPositionDelta` → честная двойная запись «узел→узел» (сейчас пишет
`bal.available` без встречной ноги, Р-8). `risk` считает `Z_a` вместо `assets−client`.

## Альтернативы

- **Один агрегат NOP (ADR-054)** — не различает исполнимость и адрес; ложные полнокапитальные
  хеджи. Оставлен как частный случай, не как единственная модель.
- **Только уровень узла без агрегата** — теряется ценовой лимит по активу; §6 показывает,
  что контроль узла — предпосылка контроля агрегата, но не заменяет его.

## Последствия

- `ledger.proto`: `GetNodeBalances`/`ApplyNodeTransfer`; PG `node_balances`.
- `risk.proto`: `GetExchangeNOP` += `target`, `in_flight`, `in_transit`, разрез по площадкам.
- Фронт: три таблицы позиции (агент/узел/актив); казначейская вкладка += `target/in_flight/in_transit`.

## Money-path: value→quantity и план≠факт (поправка владельца 2026-09-10)

Клиринг CE-агентов выдаёт потоки в **стоимости** (тыс. USDT); house-баланс ledger ведётся в
**количестве**. Три правила перевода:

1. **Конвертация по ногам, по цене узла — НЕ агрегат/марка.** `ΔQ = Σ_ноги f_leg / P_node(leg)`,
   где `P_node(a@v)` — цена узла из клиринга: узловой потенциал `x` (‰) движка
   `ce_agent_clearing` (= π, дуальная строки баланса), в абсолюте `P_node = P0_a·exp(x[a@v]/1000)`.
   Деление агрегата на марку/мид даёт систематическую однознаковую ошибку в 2–3× больше
   прибыли такта (пример владельца: −6.93…−9.80 USDT при PnL 3.68) → фантомная позиция за
   ~100 тактов. Выбор цены весит больше, чем агрегирование; делить надо ровно на ту цену, в
   которую клиринг оценил узел, иначе баланс, сведённый в стоимости, в количествах не сойдётся.
   Требует `reference_price` (P0, абсолют) на актив в `CeClearingInput` — у market_data он есть.
   (Для Newton-движка `pi`=`x` уже доступен; премиса «OSQP pi не собирается / Р-5» устарела — CN-1.)

2. **Payload с разрезом по узлу (C как состав, не альтернатива).** `ce.position.delta` →
   `AssetDelta{asset, venue, delta_qty (АВТОРИТЕТНО), price_used=P_node, delta_value=qty·price}`.
   `delta_value` — диагностика (панель PnL/аудит); `venue` даёт вкладке Clearing уровень «узел».
   «Двойной источник истины» снят: `price_used` в payload делает `value=qty·price` проверяемым.

3. **План ≠ факт (семантика).** `ce.position.delta` после клиринга — **план**, ложится в
   `committed` (ADR-058), НЕ в house-баланс. House-факт двигают только подтверждения площадок
   (`execution.reports`, шаг A8) по **фактической** цене исполнения (≠ цена узла — мёртвые зоны
   и проскальзывание). **Заменяет** первую версию этой сессии (`ApplyPositionDelta`→house,
   [ledger_uc.cpp:718](../../../cpp/ledger/src/app/ledger_uc.cpp)): без разделения при вводе A8
   позиция удвоится. Позиция = house(факт) + committed(план в пути), сверяется в `Z_a`.

## Обратимость

`Z_a` при отсутствии клиентов/запаса численно совпадает с NOP → откат к ADR-054-виду без
потери данных. Новые RPC/поля аддитивны. Тесты §7: без плеч запаса `ΔP≡0`. Money-path за
флагом; при выключении — прежний `ApplyPositionDelta`→house (переходно).
