# ADR-061: Модель позиции CE v2 — агент с нуля, полоса ±q, счёт дома

> **Статус `accepted` (владелец, 2026-09-15).** Развилки §2 плана подтверждены: движок клиринга = Newton (ADR-062), тип участника AGENT = третий `party_type` (ADR-063), номер фичи = F-18. Гейт принятия ADR снят — документарная цепочка открыта для реализации Э1. **Остаются предусловия для стадий кода** (не для документации): два security-CRITICAL (auth на `/v1/flow-orders`; `PreHedgeCheck`/kill-switch в путь venues) и golden-источники `ce_tick_v2.py`/`square_bands.py` для тест-goldens — см. [open-questions](../../02-system/features/F-18-ce-capital-position-hedge/open-questions.md). Источник решения — [CE_algorithm_v2.md](../../../incoming-docs/2026-09-15-CE_algorithm_v2.md).

## Контекст

CE (Continuous Exchange) — собственная биржа: держит оборотный капитал на нескольких внешних площадках (Binance, Kraken) и обслуживает клиентский поток, хеджируясь на этих площадках. Её внутренняя книга — это не чужие заявки, а кривые нескольких **агентов** (виртуальных контрагентов), которые сводит клиринг (расчёт равновесных потоков между агентами внутри такта; поток агента `j` за такт обозначаем `f_j`).

Действующая модель зафиксирована в **ADR-057** (трёхуровневая позиция «агент → узел → актив» с целевым инвентарём `target`). Там ненулевую позицию биржи порождало **STOCK-плечо** переводчика (ADR-055) через отдельный узел-склад `asset@__book__` (ADR-056), а от повторной отправки заявок защищало отдельное поле `committed` (ADR-058).

Владелец в `CE_algorithm_v2.md` меняет модель целиком:

- агентов остаётся **два** — **переводчик** (маркет-мейкер на одной площадке: меняет актив на деньги и обратно) и **арбитражёр** (перевозит один актив между площадками за тариф + срок доставки, ценой не торгует); **плечо запаса (STOCK) и узел-склад убраны** (узел — это пара «актив на площадке», например `BTC@Binance`);
- **позиция агента** `c_j` (накопленное клирингом, но ещё не отправленное наружу обещание; знаковая, может быть отрицательной) **стартует с нуля** и накапливается клирингом (`c ← c + f`); понятия `target` больше нет;
- позицию двигают **встречные потоки клиринга**: клиентский поток (когда есть клиенты) и встречные потоки переводчиков/арбитражёров между площадками. Собственный STOCK-остаток позицию не двигает — его нет;
- наружу CE выходит **только при выходе позиции за полосу** `q_j` (порог на модуль позиции: пока модуль `c_j` не превышает `q_j`, наружу не уходит ни одной заявки);
- прибыль оседает на **счёте дома** (техническая строка-невязка, которая балансирует книгу и забирает арбитражную прибыль; сам не агент, заявок не порождает), а не на агенте;
- **владение** биржи `Z_a` (реальный остаток по активу `a` относительно старта: `Z_a = владение(t) − владение(0)`) меняют ровно две вещи — сделка с клиентом и подтверждённое исполнение на площадке; без клиентов `Z ≡ 0`.

Текущий код (`d4900700`) уже ближе к v2, чем к первому прототипу: движок клиринга `ce_agent_clearing` даёт цены узлов напрямую, событие `ce.position.delta` публикуется сквозным потоком. Поэтому миграция — точечная (граф, накопление, эмиссия), а не переписывание солвера. Код-ревизия (сводка §10) нашла два факта в объёме v2: сдвиг якоря `σ* = m + ρ·c` в коде **отсутствует**, а поле `venue` в дельте позиции **теряется** консюмером — обе правки входят в работу.

## Решение

1. **Позиция агента `c_j`** — единственное число уровня «агент»: знаковая, старт `0`, накопление `c ← c + f` каждый такт. `target`, STOCK-плечо и узел-склад удаляются как понятия.
2. **Якорь сдвигается одним слагаемым:** `σ*_j = m_j + ρ_j·c_j` — где `m` (рыночный якорь из стакана: ставка, вокруг которой агент котирует) сдвигается на `ρ·c` (снос котировки от собственной позиции; `ρ` — коэффициент сноса). Коэффициенты: `ρ = 0,004` у переводчика, `ρ = 0,002` у арбитражёра. Якорь видит позицию агента **до** накопления текущего такта.
3. **Что двигает позицию.** Позицию `c_j` двигают встречные потоки клиринга — клиентский поток (когда клиенты есть) и встречные потоки переводчиков/арбитражёров между площадками. Без клиентов клиентского потока нет, но межплощадочные встречные потоки позицию двигать могут. Неподвижным без клиентов и без исполнения остаётся **владение** `Z` (`Z ≡ 0`), **а не** позиция `c_j`. *(Инвариант INV-CE-A0, проверяется тестом; см. план тестов F-18 v2.)*
4. **Полоса `±q_j`: эмиссия и изменение позиции разнесены** (решение владельца 2026-09-15). При `|c_j| > q_j` наружу уходит хедж-заявка на избыток `(|c_j| − q_j)·sign(c_j)`. Позицию `c_j` **уменьшаем по факту исполнения** (в т.ч. частичного), а НЕ в момент эмиссии. Отправленное держим в `in_flight` (часть позиции, уже отправленная наружу, но ещё не исполненная), чтобы следующий такт не отправил его повторно. По исполнению `fq` убывают и `c_j`, и `in_flight`; по таймауту `in_flight` освобождается, а позиция не меняется (см. раздел «Конфликт со спекой»). Полосу проверяем по свободной части позиции — избытку сверх `q_j`, ещё не покрытому `in_flight`. Полосы разные по смыслу: переводчик `q = 18` (риск незахеджированного запаса), арбитражёр `q = 30` (размер партии перевоза). Размер заявки считаем по стоимости, тип — по экспозиции.
5. **Счёт дома — не агент.** Это техническая строка-невязка в узле нумерария (опорный узел-деньги `USD@Binance`, относительно которого меряются все цены; его цена закреплена нулём): у неё нет якоря, наклона, полки и полосы, заявок она не порождает. Она забирает арбитражную прибыль (равную разнице цен площадок) и балансирует книгу. Ключ дома — отдельный зарезервированный псевдо-узел, а не суффикс `@__book__` (чтобы не ломать разбор строк вида `ASSET@VENUE`).
6. **Тип участника AGENT** — третий вид участника рядом с CLIENT и HOUSE, а не подтип клиента. У AGENT позиция знаковая, нет требования неотрицательности и нет пары резерв/освобождение; проверка резерва остаётся только для CLIENT. Архитектурно оформляется отдельным ADR-063, здесь фиксируется как инвариант.
7. **Хранение.** Таблица `ce_agent_position(agent_id, asset, venue)` с полями `position` (знаковая) и `in_flight` (знаковая), плюс `updated_at`, `last_batch_id`. Владелец — `ledger` (CLAUDE.md §17). `position` меняется по исполнению (A8), `in_flight` растёт при эмиссии (A7) и убывает по исполнению/таймауту. Прежнее поле `committed` (ADR-058) переезжает сюда как `in_flight` (см. раздел «Конфликт со спекой»).

### Флаги реализации

Все флаги по умолчанию выключены и снимаются независимо (план этапов Э1–Э5).

| Флаг | Этап | Что включает |
| --- | --- | --- |
| `CE_V2_GRAPH` | Э1 | Граф только из площадок плюс счёт дома; STOCK-плечо и узел-склад убраны. |
| `CE_AGENT_POS` | Э2 | Позиция агента с нуля, знаковая; сдвиг якоря `σ* = m + ρ·c`. |
| `CE_AGENT_BAND` | Э3 | Эмиссия только при выходе за полосу; отправленное учитывается в `in_flight`. |
| `CE_AGENT_A8` | Э4 | Подтверждения и таймауты: декремент позиции по исполнению, освобождение `in_flight`. |
| `CE_TRANSFER_AGENT` | Э5 | Арбитражёр как перевоз актива (событие `ce.transfers`, автомат состояний доставки). |

**Зависимость:** `CE_AGENT_A8` — жёсткий пререквизит включения `CE_AGENT_BAND`. Без обработки таймаута отвергнутая или просроченная заявка навсегда занизила бы позицию. Э4 — не доработка после Э3, а предусловие Э3 в бою (security-замечание MEDIUM-7).

## Альтернативы

1. **Сохранить target-модель ADR-057 и добавить полосу поверх.** Отклонено: два конкурирующих механизма возврата к нулю (порог `θ` от `target` и полоса `q` от нуля) дают неоднозначный стимул и противоречат явному «`target` в v2 отсутствует».
2. **Сделать AGENT клиентом с разрешённым отрицательным балансом.** Отклонено: ломает инварианты CLIENT (неотрицательность, резерв, идемпотентность заказа, CLAUDE.md §8.2); нужен отдельный тип участника (ADR-063).
3. **Оставить STOCK-плечо ради обратной совместимости NOP-метрики.** Отклонено: v2 убирает склад; дублирование механизма, который теперь закрывает счёт дома, — источник рассинхрона.
4. **Держать `committed` отдельной теневой копией позиции ради аудита.** Отклонено как отдельная сущность: аудит закрывает `clearing_trace` (ADR-059). При этом `in_flight` остаётся как рабочее поле, но это часть позиции, а не её теневая копия.
5. **Удалить файл ADR-057 вместо supersede.** Отклонено: документы — неизменяемый след; ADR-057 остаётся со статусом «superseded by ADR-061».

## Последствия

### Положительные

- Проще ментальная модель: одна знаковая позиция плюс `in_flight` вместо триады `qty/target/committed`; уходит конфиг-поверхность `CE_TARGET_*` и `CE_STOCK_*`.
- Прямое соответствие эталону `ce_tick_v2.py` (27 проверок) снижает модельный дрейф, дважды зафиксированный ранее.
- Счёт дома даёт проверяемый инвариант баланса книги (ранг матрицы и число независимых циклов), покрываемый тестом.

### Отрицательные и издержки

- Ломающие контракты (отдельным координированным PR, отдельно от кода): `risk.proto` (убрать `target` из ExchangeNOP), `treasury.proto` (`AssetDelta → AgentDelta` с `agent_id`, `agent_kind`), новый `ce.transfers`. Потребители и фронт мигрируют вместе.
- Требуется исправить действующий баг: поле `venue` в дельте позиции теряется консюмером, а позиция ключуется только по активу — узловой разрез не сходится. Ключ переходит на `(agent_id, asset, venue)`.
- Переходный период держит две модели `Z_a` (старую target-based и новую zero-based) — обязательно за флагом, без молчаливой подмены (CLAUDE.md, правило конфликтов).
- Операторам нужно явно сообщить: агенты — это обещания дилерского клиринга, а не директивная собственная книга биржи; семантика «вернуть к настроенному нейтральному инвентарю» уходит.

## Обратимость

Средняя, откат безопасен:

- Все пять флагов по умолчанию выключены; при выключенных флагах поведение идентично текущему.
- `git revert` безопасен: новые таблица и поля аддитивны, старые не трогаются.
- Старый путь `ce_committed_` сохраняется на время миграции (не удаляется в тех же PR, что вводят новую таблицу) — переключение только флагом, данные не теряются.
- Для ломающих контрактов рекомендуется переходное окно с полем `target`, помеченным `deprecated`, а не жёсткое удаление сразу.

## Конфликт со спекой: учёт позиции по исполнению (решение владельца 2026-09-15)

Исходник `CE_algorithm_v2.md` §A7 предписывает: при выходе за полосу **сразу** уменьшить `c_j` на отправленный избыток (позиция становится ровно `±q`), заявку положить в `in_flight`, а по таймауту неисполненный остаток вернуть в позицию по плановой цене; и явно — «отдельного `committed` не нужно».

**Владелец переопределяет:** позицию `c_j` менять **по результату исполнения** (в том числе частичного) хедж-заявки, а не в момент эмиссии. Отправленное держится в `in_flight` как защита от повторной отправки; по мере исполнения убывают и `c_j`, и `in_flight`; по таймауту `in_flight` освобождается, а позиция не меняется.

- **Итоговая установившаяся позиция совпадает** в обоих подходах (`c_j = c₀ − Σ исполнено`). Различие — в промежуточном учёте (когда именно уменьшается позиция) и в механизме защиты от двойного хеджа (спека: «позиция уже на границе `±q`»; здесь: «следим за `in_flight`»).
- **Для ревизии ADR-058:** `committed` не сливается полностью с позицией — сохраняется как поле `in_flight` со смыслом «отправлено, не исполнено».
- **Для данных и тестов:** таблица получает колонку `in_flight`; инвариант «после эмиссии `|c_j| = q`» заменён на «после **полного** исполнения `|c_j| = q`»; «возврат остатка в позицию по таймауту» заменён на «освобождение `in_flight` без изменения позиции».
