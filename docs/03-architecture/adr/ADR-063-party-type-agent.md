# ADR-063 — Тип участника AGENT

> **Статус `proposed`.** Открытый вопрос из гейта §13 сводки [F-18-v2-agents-review-summary](../../implementation-plan/F-18-v2-agents-review-summary.md); решение за владельцем. Оформляет пункт 6 решения [ADR-061](ADR-061-ce-v2-agent-position-band-hedge.md).

## Контекст

`ledger` (сервис-владелец балансов и позиций) сегодня различает два вида участника:

- **CLIENT** — счёт пользователя: баланс неотрицателен (проверяется `CHECK`), под заявку средства резервируются и затем освобождаются (пара reserve/release), команды идемпотентны.
- **HOUSE** — собственный счёт биржи (определяется по `user_id == kHouseAccountId`): держит капитал и venue-остатки.

CE v2 вводит третий вид — **AGENT** (виртуальный контрагент: переводчик или арбитражёр, за которым стоит сама биржа). Его учёт принципиально иной: позиция `c_j` **знаковая** (может быть отрицательной), стартует с нуля, у неё нет требования неотрицательности и нет пары резерв/освобождение — это дилерский инвентарь, а не клиентский счёт.

Смоделировать AGENT как CLIENT с разрешённым отрицательным балансом нельзя: это ломает инварианты CLIENT (§8.2 CLAUDE.md — неотрицательность, резерв-чек, идемпотентность заказа), которые защищают деньги реальных пользователей. Нужен явный отдельный тип участника, чтобы правила CLIENT не применялись к AGENT и наоборот.

## Решение

**Ввести явный тип участника `party_type` со значениями `CLIENT` / `HOUSE` / `AGENT`; правила CLIENT (неотрицательность, резерв) применять только к CLIENT.**

- **Контракт.** Общий enum `PartyType { PARTY_TYPE_UNSPECIFIED = 0, CLIENT = 1, HOUSE = 2, AGENT = 3 }` в `fob/common/v1/common.proto` (аддитивно; пустое поле трактуется как CLIENT для обратной совместимости). `ledger.ReserveFundsRequest` получает поле `party_type` (по умолчанию CLIENT).
- **Семантика AGENT.** У AGENT знаковая позиция, нет неотрицательности, нет reserve/release. `ReserveFunds` для `party_type == AGENT` — no-op (успех без записи в резервы и без трогания баланса): учёт агента ведёт таблица `ce_agent_position` (ADR-061), а не резервы. Резерв-чек остаётся только для CLIENT; HOUSE-операции сохраняют текущее поведение (определяются по `kHouseAccountId`).
- **Хранение.** CLIENT/HOUSE живут в существующем счётном субстрате (`accounts`); AGENT — в отдельной таблице `ce_agent_position` (несовместимые инварианты: знаковая позиция без `CHECK ≥ 0`), а не в `accounts`. Разграничение пространств идентификаторов: `agent_id` не должен пересекаться с `user_id`/`account_id` (в т.ч. с `kHouseAccountId`) — фиксируется как инвариант и проверяется на входе order_flow/gateway (см. security-замечание сводки, CRITICAL-1).
- **Кто проставляет `party_type`.** Явно вызывающая сторона: `order_flow` — CLIENT, пути CE (matching/risk) — AGENT, сам ledger для house-операций — HOUSE. Тип не выводится эвристикой.

Изменение за флагами v2 (ADR-061, по умолчанию выключены): пока путь AGENT не включён, поведение ledger идентично текущему (всё трактуется как CLIENT/HOUSE).

## Альтернативы

- **AGENT как CLIENT с разрешённым отрицательным балансом.** Отклонено: ломает инварианты CLIENT (неотрицательность, резерв, идемпотентность), которые защищают деньги пользователей.
- **AGENT как HOUSE-субсчёт.** Отклонено: у HOUSE иная семантика (капитал/venue-остатки, свои проводки); смешение затрудняет аудит и путает разграничение прав.
- **Не вводить тип, различать по префиксу идентификатора.** Отклонено: неявная классификация по строке хрупка и опасна (это ровно тот механизм, что позволяет обойти разграничение — CRITICAL-1); тип должен быть явным полем.

## Последствия

- Аддитивное поле контракта (`PartyType`) и явная развилка в `ReserveFunds`.
- Инвариант непересечения `agent_id` с `user_id`/`account_id` — предпосылка безопасности (иначе клиентский путь мог бы действовать «за» агента/дом).
- Тест: `ReserveFunds` с `party_type = AGENT` всегда успешен и не создаёт записи в резервах (нет побочных эффектов); CLIENT-путь неизменен.

## Обратимость

Аддитивно и за флагом: при выключенном пути AGENT поле `party_type` не влияет на поведение (всё как CLIENT/HOUSE сегодня). `git revert` безопасен — новое поле и развилка не трогают существующие CLIENT/HOUSE-проводки.
