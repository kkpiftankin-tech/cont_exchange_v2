# ADR-070 — Быстрая полоса стакана в venues

> **Решение владельца (2026-10-06):** панель «Торговля» показывает сырой стакан
> биржи, и он обновляется слишком медленно (снимок старше 10–25 с). Выбран
> вариант A — отдельная «быстрая полоса» опроса стакана внутри `venues`.

## Термины

- **Снимок (snapshot)** — один ответ REST `depth` биржи, нормализованный в
  `VenueSnapshot` и сохранённый в ClickHouse `venue_snapshots`; из него панель
  «Торговля» читает уровни стакана (BFF `/api/venues/orderbook`).
- **Основной цикл (`md_publish_loop`)** — обходит все пары всех бирж по очереди;
  на каждую пару делает до трёх REST-вызовов (стакан, тикер 24h, лента сделок),
  публикует снимок в Kafka `venue.snapshots` и строит кривую ликвидности для
  клиринга. Цикл на Binance занимает ~26 с, поэтому снимок каждой пары старше
  до 26 с.
- **Быстрая полоса (`depth_fast_loop`)** — новый поток: для заданной биржи и
  списка пар делает только один REST-вызов `depth` и сохраняет нормализованный
  снимок в хранилище.
- **ADR-060** — реалистичное исполнение симулятора по ленте публичных сделок;
  лента читается основным циклом, быстрая полоса её не трогает.

## Контекст

Замеры на dev (2026-10-06): период снимка пары Binance ≈ 25,5 с, возраст при
чтении 0–26 с; лимит REST не исчерпан, ~2 с уходит на одну пару (3 вызова +
построение кривой), цикл завершается сном 5 с (`VENUES_MD_LOOP_INTERVAL_MS`).
Поднять каденс основного цикла нельзя без риска для ленты сделок (ADR-060,
голодание REST-бюджета) и для клиринга, который читает `venue.snapshots`
(`market_data`).

## Решение

1. Добавить в `venues` потоки `depth_fast_loop` (по одному на биржу), по образцу
   `extra_ticker_loop`. Настройка через env: `VENUES_FAST_DEPTH_VENUE` (CSV бирж или
   `*` = все CEX; DEX не поддерживает глубокий запрос; пусто = выключено),
   `VENUES_FAST_DEPTH_SYMBOLS` (CSV `BASE/QUOTE`), `VENUES_FAST_DEPTH_INTERVAL_MS`
   (пауза между проходами, по умолчанию 1000), `VENUES_FAST_DEPTH_LEVELS`.
2. Запрос идёт под тем же per-venue мьютексом `RequestSnapshot` и через тот же
   REST-лимитер адаптера (см. п. 3).
3. Глубину быстрой полосы задаёт `VENUES_FAST_DEPTH_LEVELS` (по умолчанию 1000),
   независимо от `depth_levels` биржи (20 — вход клиринга). Для этого адаптер
   получает метод `RequestDepthOnly(request, levels)`: один REST-вызов глубины
   **без изменения состояния адаптера** (LOB/`books_`), без тикера и ленты сделок,
   с тем же REST-лимитером и circuit breaker. Замер Binance BTC/USDT:
   1000 уровней ≈ 150–196 BTC накопленного объёма (диапазон ≈ ±$200).
4. Результат нормализуется тем же нормализатором и **пишется только в отдельную
   таблицу `venue_book_live`** (ClickHouse, TTL `VENUES_CLICKHOUSE_LIVE_BOOK_RETENTION_HOURS`,
   по умолчанию 2 ч). В Kafka `venue.snapshots`, `venue_snapshots` (TTL 90 дней) и
   кривые ликвидности он **не попадает**; клиринг и CE-цепочка работают как раньше.
   BFF `/api/venues/orderbook` берёт более свежий снимок из `venue_book_live` и
   `venue_snapshots`.

## Альтернативы

- **B. Подкрутить `VENUES_MD_LOOP_INTERVAL_MS` / `CEX_REST_RPS`** — выигрыш
  небольшой (узкое место — последовательный обход и три вызова на пару), риск
  бана по лимитам.
- **C. BFF сам ходит на публичный REST биржи** — мгновенно, но обходит `venues`
  (панель покажет не то, что видит система) и требует парсер на каждую биржу.
- **Публиковать быстрые снимки в `venue.snapshots`** — изменило бы вход
  `market_data`/клиринга и нагрузку; отвергнуто для изоляции.

## Последствия

- Возраст снимка выбранных пар падает с ~26 с до порядка 1–3 с.
- Плюс ~N REST-вызовов за проход на выбранные пары (N = число пар); для Binance
  допустимо, для строгих бирж (Kraken) не включать.
- **Все CEX (решение владельца 2026-10-07).** Глубина ограничивается API биржи:
  Binance до 1000 (в конфиге), Kraken `count` ≤ 500, OKX `sz` ≤ 400; Coinbase
  `level=2` отдаёт книгу целиком — обрезается до `VENUES_FAST_DEPTH_LEVELS`. Бюджет
  REST по умолчанию на биржу: binance 5, okx 5, coinbase 3, kraken 1 запрос/с
  (`<PREFIX>_FAST_DEPTH_RPS` или общий `VENUES_FAST_DEPTH_RPS`). При узком бюджете
  (kraken: 5 пар на 1 запрос/с) пары обходятся по кругу — свежесть пары ≈ N/RPS.
  Отказы REST (например, недоступная из дев-сети биржа) логируются первым и каждым
  30-м, чтобы не засорять логи.
- Быстрая полоса **не делит** с основным циклом ни REST-токены, ни circuit breaker:
  у неё свой token bucket (`VENUES_FAST_DEPTH_RPS`, по умолчанию 5 запросов/с) и
  выделенный REST-клиент (не ждёт общий мьютекс `RequestSnapshot`); её ошибки и
  успехи в breaker не пишутся (при открытом breaker биржи полоса просто молчит).
  Общим остаётся лимит самой биржи: Binance считает вес по IP, запрос на 1000
  уровней стоит 10 единиц — включать только для бирж с запасом (Binance), не для
  строгих (Kraken).
- Глубокий снимок ≈ 70 КБ JSON на строку (1000 уровней × 2 стороны): поэтому отдельная
  таблица с TTL в часах, а не `venue_snapshots` (90 дней). При ошибке REST быстрая
  полоса ничего не пишет (устаревший кэш адаптера не выдаётся за свежий стакан).
- Поле `volume_24h` в быстрых снимках равно 0 (тикер не запрашивается); панель
  «Торговля» его не использует.
- Вес запроса Binance depth: limit 1000 = 10 единиц; 5 пар за проход ≈ 50 единиц
  против лимита 6000/мин.
- Панель «Торговля» показывает снимок свежее, чем тот, по которому в этот же
  момент построена кривая клиринга (кривая — по основному циклу).
- Число уровней стакана по-прежнему задаётся `depth_levels` биржи (20 по
  умолчанию); это отдельное решение.

## Обратимость

Высокая: выключается пустым `VENUES_FAST_DEPTH_VENUE`, схем и контрактов не
меняет.

## Дополнение 2026-10-07: кривые ликвидности по запросу (M1–M4)

**Решение владельца:** на панели «Торговля» по чекбоксу показывать кривые ликвидности тем
же расчётом, что на вкладке Clearing, но без прежнего ограничения стакана (20 уровней) и
не в цикле, а **по сигналу с фронта**.

- **Расчёт.** Четыре способа снятия наклона §6.2 — M1 касательная, M2 МНК, M3 по выгоде,
  M4 минорант (формулы — `docs/04-domain/business-rules.md`, R-F05A-003; код —
  `cpp/venues/src/app/liquidity_curve_producer.cpp`). По каждой стороне стакана
  снимается α, берётся `α_ext = min(bid, ask)`, наклон прямой `β = mid²/(10⁴·α_ext)`
  (θ=1, чтобы кривые способов были сравнимы с VWAP). Кривая — **одна прямая на обе
  стороны**: `P(q) = anchor + β·q`, `anchor = mid`, `q` со знаком (ask +, bid −); на графике
  рисуется на всю ось цены.
- **Один источник.** Новая функция `ComputeSlopeMethods(snapshot, max_levels)` — та же
  логика, что в `SetSafeTranslator` (общий `SnapshotMidForSlopes`, общий
  `RawSideAllMethods`); формулы не продублированы ни в BFF, ни во фронте.
- **По запросу.** `venues` хранит последний глубокий снимок каждой пары быстрой полосы в
  памяти; HTTP `GET /api/v1/venues/{venue}/slope-curves?symbol=&levels=` считает кривые в
  момент запроса. BFF `GET /api/venues/slope-curves` проксирует и добавляет выбранный
  клирингом способ (`f05a_clearing_config.slope_method`). Фронт при клике на чекбокс
  запрашивает расчёт и пока способ включён обновляет его раз в 3 с.
- **Глубина.** Без ограничения: все уровни глубокого снимка (до 1000 у Binance, 500 у
  Kraken, 400 у OKX); `levels=N` ограничивает N лучшими уровнями каждой стороны.
- **Клиринг не затронут:** клиринговый путь (`SetSafeTranslator` по 20 уровням в цикле)
  не менялся; расчёт по запросу ничего не публикует и не пишет.
- **Предупреждение §6.3.** M1–M3 могут локально переобещать глубину; безопасен минорант
  (M4). На панели способ, идущий в клиринг, отмечен ★.

## Дополнение 2026-10-08: динамический режим (аренды) вместо «всегда включено»

**Контекст.** Статический режим «4 CEX × 5 пар × 1000 уровней / 1 с» (20 запросов/с) на dev
грузил `venues` на 300%+ CPU и голодал ленту публичных сделок: хеджи CE не исполнялись,
позиции стояли. Режим выключили. Панель «Торговля» нужна для верхнеуровневой оценки
динамики бирж **не постоянно**, поэтому глубокий опрос должен включаться динамически
и сам гаснуть.

**Решение владельца (2026-10-08):** динамически подключаемый режим для **всех** бирж.

- **Аренда.** Панель при включённом «Живом режиме» раз в ~10 с шлёт `POST /api/venues/depth-watch`
  с набором `(venue, symbol)` и сроком (30 с). `venues` ведёт реестр аренд
  (`DepthWatchRegistry`) и опрашивает **только арендованные пары**. Сигналы прекратились
  (режим выключили, вкладку закрыли) — аренда истекает, опрос гаснет сам, явной команды
  «стоп» не нужно. Продление не сокращает остаток аренды; срок ограничен 5–60 с.
- **Потолок нагрузки по построению.** Одновременно арендованных пар не больше
  `VENUES_FAST_DEPTH_MAX_WATCH` (по умолчанию 8, суммарно по всем биржам): 8 пар раз в 2 с —
  это ≈4 запроса/с против 20, из-за которых режим выключили. Сверх потолка новые пары
  отклоняются (UI показывает «N пар не принято»), существующие продлеваются.
- **Охват в UI:** «эта пара на всех биржах» (до 4 CEX) или «все пары этой биржи» (до 5).
  «Все биржи × все пары» (20) намеренно недоступно — выше потолка.
- **Простой.** Без аренд поток биржи спит (опрос раз в 0,5 с проверяет реестр): нулевая
  нагрузка. Потоки поднимаются для всех CEX-адаптеров; DEX глубокий запрос не поддерживает.
- **Статический режим** (`VENUES_FAST_DEPTH_VENUE`) сохранён как «всегда включено» для
  перечисленных бирж, по умолчанию пуст.
- **Устаревание.** Расчёт кривых по запросу отказывает (`deep_book_stale`), если глубокому
  снимку больше `VENUES_DEEP_BOOK_MAX_AGE_MS` (30 с): после истечения аренды им пользоваться
  нельзя. BFF `/api/venues/orderbook` берёт более свежий из live-таблицы и основного
  снимка, поэтому после выключения режима панель честно возвращается к 20 уровням.
- **Безопасность.** Ручка аренды — внутренний admin-API `venues`, наружу ходит только через
  BFF; она не меняет деньги, клиринг и торговые решения, а лишь включает чтение рыночных
  данных биржи. Ввод валидируется (формат `BASE/QUOTE`, не более 64 элементов, только
  известные CEX); аудит как для операторских действий (kill-switch) не требуется.

**Замечания ревью (2026-10-08) и решения.**
- Ввод ручки аренды: типы полей проверяются явно, `ttl_ms` ограничивается до приведения к
  целому, любые ошибки разбора — HTTP 400 (порт admin доступен и напрямую, не только через BFF).
- Символ нормализуется к верхнему регистру и требует ровно один `/` (`btc/usdt` и `BTC/USDT` —
  одна аренда); иначе дубликаты вытесняли бы легитимные пары под потолком.
- Аренда короткая (6 с) и подтверждается каждые 2,5 с: при смене пары или охвата старые аренды
  освобождают место за ≤6 с, а не за 30 с.
- Глубокий снимок пары удаляется из памяти, когда пара выпала из набора (аренда истекла).
- **Принятый риск (требует решения владельца): ручка аренды без аутентификации.** BFF-роут
  `/api/venues/depth-watch` и порт admin `venues` не требуют авторизации, как и остальные
  read-only роуты BFF. Любой клиент BFF может продлевать аренды бесконечно и держать до
  `VENUES_FAST_DEPTH_MAX_WATCH` пар круглосуточно; нагрузка ограничена потолком, а не временем.
  Допустимо, пока BFF закрыт сетью (Tailscale). Если режим считать операторским действием
  (CLAUDE.md §1.7), нужны авторизация и audit-запись.
- В простое каждая CEX-биржа держит поток и один пустой REST-клиент (curl-хэндл на вызов, без
  соединений), запросов нет.

## Дополнение 2026-10-08 (3): кривые ликвидности по всем биржам и суммарные

**Решение владельца:** на панели «Торговля» по чекбоксам показывать (1) кривые ликвидности
выбранной валюты (пары) на всех биржах, (2) суммарную кривую всех бирж, (3) суммарную кривую
всех бирж минус выбранная биржа.

- Для каждой CEX-биржи BFF (`GET /api/venues/slope-curves-all`) запрашивает у `venues` расчёт
  способа §6.2 по её глубокому стакану (тот же `ComputeSlopeMethods`) и суммирует линейные
  функции ликвидности `q_i(p)=(p−mid_i)/β_i` — формула агрегата с вкладки Clearing (ADR-053),
  вынесена в `slope_aggregate.js` с тестом. Способ один для всех бирж: выбирается в панели,
  по умолчанию — клиринговый (★).
- Нужны глубокие стаканы всех бирж пары ⇒ чекбоксы автоматически включают «Живой режим» с охватом
  «эта пара на всех биржах» (аренды, потолок `VENUES_FAST_DEPTH_MAX_WATCH`). Пока аренда не
  дошла до биржи, она в `missing`, а суммарная кривая считается по остальным — UI прямо
  показывает «учтено N из M».
- Расчёт на каждый запрос (раз в 3 с), ничего не публикуется и не пишется; клиринг не затронут.
