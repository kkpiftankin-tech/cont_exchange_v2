# ADR-071 — Inventory-skew на ноги арбитражёра

> **Решение владельца (2026-10-07):** позиция CE-агента НЕ блокируется клирингом,
> даже если хедж на внешнюю биржу не подтвердился и внутренняя позиция растёт;
> её ограничивает **сдвиг якоря к цене непрерывного метчинга** (inventory-skew),
> зависящий от суммарной позиции (внутренняя − подтверждённая внешняя). Этот
> сдвиг нужно распространить на **ноги арбитражёра `A_*`**, а не только на
> переводчиков `T_*`.

## Термины

- **База skew** `b_e = c_e + w_e` — для ребра `e`: `c` (position) + `w` (in_flight).
  Под моделью A7 (ADR-061): эмиссия хеджа `c→w` (сумма неизменна), подтверждённый
  fill `w−=filled` (сумма падает), таймаут/реджект возвращает остаток `w→c` (сумма
  неизменна). Итого `b = I − F`, где `I`=Σ потоков клиринга, `F`=Σ **подтверждённых**
  fill'ов. То есть `b` = «внутренняя накопленная − подтверждённая внешняя» (нетто-
  экспозиция). Внешняя подтверждённая позиция уже видна на «Живых позициях» как
  «сделки: база/квота».
- **Сдвиг якоря** `a^{eff}_e = a_e − clamp(γ_e·b_e, −K_e, K_e)`. У QUOTE-ребра
  `a_e` — котировочный якорь; у TRANSFER-ребра `a_e=0` ⇒ сдвиг = чистый
  inventory-anchor `−clamp(γ_A·b_A)`.

## Контекст

IN-017 задаёт якорь дилера `a* = P − A·q`, где `q` — **суммарный** инвентарь
дилера; каждый агент должен иметь свой инвентарный член. В CE обратная связь
позиция→цена (`matching_loop.cpp`, `anchor −= clamp(γ·b)`) применяется **только к
`T_*`** (QUOTE-рёбра); ноги арбитражёра `A_*` (TRANSFER-ребро, `anchor=0`,
ADR-069) её не получают. Косвенного ограничения нет: сдвиги переводчиков зависят
от их собственного инвентаря `b_T` и ничего не знают о `b_A`; если переводчики
плоские/насыщены, спред узлов не закрывается и `b_A` растёт без предела.
Наблюдаемо: при неподтверждённом хедже позиция арбитражёра растёт и не
самоограничивается.

## Решение

Распространить тот же inventory-skew на TRANSFER-рёбра:

$$a^{eff}_e = a_e - \mathrm{clamp}(\gamma_e\, b_e,\ -K_e,\ K_e),\qquad b_e = c_e + w_e = I_e - F_e$$

- `e` пробегает QUOTE (`T_*`) И TRANSFER (`A_*`). Для `A_*`: `a_e=0` ⇒
  `a^{eff}=−clamp(γ_A·b_A)`.
- **База ноги арбитражёра** — позиция dst-ноги (приёмник `j`, узел `e.v`):
  ключ ledger `(agent_id, asset, venue_j)`, `b_A = c_j + w_j`. Знак: положительное
  накопление на приёмнике снижает поток `i→j` (разворот, mean-reversion).
- Внедрение — в `AssembleCeGraphV2` (у TRANSFER-ребра нет якоря в
  `CeClearingInput`): новый необязательный параметр `inv_basis` (ключ
  `"agent_id|venue"`→`b`) + `γ_A` + `K_A`; якорь ребра = `−clamp(γ_A·b_A)`.
  `FetchAgentPositionsCached` уже отдаёт `A_*` (чинится двойной ключ по venue —
  раньше две ноги схлопывались по `agent_id`).
- **Отдельные `γ_A` / `K_A`** (глубина transfer-ребра иная, чем у QUOTE):
  `f05a_clearing_config.ce_arb_inv_skew_gamma/_max_pm`, live-настройка; env-fallback
  `CE_ARB_INV_SKEW_GAMMA` / `CE_ARB_INV_SKEW_MAX_PM`. `γ_A=0` ⇒ поведение как раньше.
- База `T_*` (ADR-066) и учёт A7 (ADR-061) **не трогаются**.

## Альтернативы

1. **Блокировать приём клиринга при пробое band.** Отклонено (владелец): позиция
   должна иметь право расти; ограничитель — цена, не блокировка.
2. **Полагаться на skew-цены узлов от переводчиков (косвенно).** Отклонено:
   не гарантирует ограниченность `A_*` (переводчики плоские ⇒ спред не закрыт,
   `b_A` растёт); накопление арбитражёра невидимо всем skew-членам.
3. **[Выбрано] Прямой inventory-anchor на TRANSFER-ребре** по его базе `b_A`.

## Последствия

- Ноги арбитражёра самоограничиваются сдвигом якоря (как переводчики); при
  неподтверждённом хедже рост `b_A` усиливает сдвиг → поток разворачивается.
- **Ограниченность условна от `K_A`:** если равновесный сдвиг > `K_A`, накопление
  снова ограничено лишь клэмпом. `K_A` делаем с запасом и настраиваемым.
- Money-path (вход клиринга) ⇒ `code-reviewer`. Контракты/ledger-учёт не меняются
  (внешняя позиция уже = подтверждённые fill'ы, A7).
- Схема: 2 колонки в `f05a_clearing_config` (ALTER на dev + init.sql для свежих БД).

## Инварианты (проверяются тестами)

- I1: `b = I − F`; `F` движется ТОЛЬКО на подтверждённом fill'е.
- I2: send/reject/expire не меняют `b` (неисполненный остаток возвращается в `c`).
  Conservation-тест: `Δ(c+w) = поток_клиринга − подтверждённый_filled` на КАЖДЫЙ
  статус execution_report (ловит утечку in_flight при EXPIRED/REJECTED).
- I3: `sign(shift)=sign(b)`, `|shift|≤K`.
- I4: `γ_A=0` ⇒ побайтово старое поведение (безопасно за флагом).
- I5: знак для TRANSFER-ребра `i→j`: положительное накопление на `j` уменьшает
  поток `i→j` (фиксируется тестом).

## Обратимость

Высокая. `γ_A=0` → старое поведение; откат — убрать параметр ассемблера и колонки.
Контрактных/ledger-миграций нет.
