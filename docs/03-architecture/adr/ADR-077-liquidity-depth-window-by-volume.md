# ADR-077 — Окно глубины стакана по объёму

> **Статус: proposed.** Источник требования — владелец (2026-10-15): «для расчёта кривой ликвидности нужно брать не 20 уровней, а рассчитывать глубину в соответствии с документом». Документ — PDF «Глубина стакана для калибровки ликвидности» (7 октября 2026). В `incoming-docs/` он пока не зарегистрирован (кандидат на номер IN-019, регистрация — по явной просьбе владельца). Формулы шагов 2–3 документа переносятся сюда с пояснениями; шаг 1 документа (методика оценки среднего размера сделки) ведётся отдельно.

## Контекст

Кривая ликвидности площадки (ADR-053: наклон и якорь агента-переводчика CE считаются из сырого стакана площадки по формулам §6.2, четыре способа снятия наклона M1–M4) строится в цикле `venues` по **фиксированным 20 уровням** стакана. Число 20 зашито в трёх местах: конфиг площадки `venue_config.depth_levels`, лимит REST-запроса стакана (`rest_depth_url` берёт максимум из `depth_levels` и `lob_max_levels`, по умолчанию 50) и обрезка снимка перед публикацией. Локальный сборщик стакана (`CexLocalLobAssembler`) тоже держит только верхние `lob_max_levels` уровней, так что даже при увеличении `depth_levels` глубже 50 уровней данные не пройдут.

Документ о калибровке глубины объясняет, почему это неверно: наклон кривой должен измеряться **на масштабе реальной сделки**, а число уровней, покрывающее такой масштаб, у разных площадок и пар различается на порядки. Окно задаётся объёмом $V_{cal}=k\cdot\bar q$, где $\bar q$ — средний размер мета-ордера (крупной сделки, которую исполняют по частям) по паре на площадке, а $k$ — один глобальный множитель (в документе рекомендовано 10, допустимо 3–30).

Измерение на живых стаканах 2026-10-15 (константы документа, $k=10$; размер окна по формулам ниже):

| --- | --- | --- | --- | --- |
| Binance BTC/USDT | ≈ 12,7 | 1,0 % | больше 1000 уровней | 79 % |
| Binance ETH/USDT | ≈ 8,5 | 0,9 % | больше 1000 уровней | 98 % |
| Binance SOL/USDT | ≈ 5,3 | 22 % | ≈ 530 уровней | 165 % |
| OKX BTC/USDT | ≈ 8,8 | 1,6 % | больше 400 уровней | 63 % |
| OKX ETH/USDT | ≈ 6,1 | 1,7 % | больше 400 уровней | 76 % |
| Kraken BTC/USDT | ≈ 2,5 | 8,0 % | ≈ 220 уровней | 216 % |
| Kraken ETH/USDT | ≈ 1,7 | 4,1 % | ≈ 130 уровней | 257 % |

Четыре вывода из измерения. Первое: 20 уровней покрывают от 1 % до 22 % нужного объёма, то есть текущая кривая отражает только верх стакана. Второе: при $k=10$ для самых ликвидных пар лимит самого API (Binance 1000 уровней, OKX 400, Kraken 500) не покрывает окно — это ловушка «обрезанный API» из документа; такой случай обязан помечаться, а не экстраполироваться. Третье: оценка $\bar q$ по формулам инвариантности заметно дрейфует — для Binance BTC/USDT три замера за час дали 1,17, 1,27 и 0,75 млн USD, потому что в формулу входит дневная волатильность, а она обновляется каждую минуту, поэтому сглаживание и гистерезис обязательны. Четвёртое: способы M1 (касательная к первому уровню) и M4 (минимум отношения глубины к сдвигу цены по всем уровням) определяются верхом стакана и почти не зависят от окна — у Kraken M4 при любом окне равен значению первого уровня; чувствительны к окну M2 (метод наименьших квадратов) и M3 (площадь прибыли). Дефолт клиринга — M4, поэтому одно только окно по объёму его не изменит; см. раздел «Этап B».

Пятый вывод — самый важный: агенты CE (`market_data`, `agent_builder.hpp`) считают глубину переводчика сами, не через `slope_method`: $\mathrm{depth}=\theta\cdot\min(\alpha_{bid},\alpha_{ask})$, где $\alpha_{side}=\min_i D_i/\delta_i$ по уровням кривой стороны (цена уровня, смещение в ‰). Вывод: **одно окно по объёму (этап A) клиринг CE практически не изменит** — оно даёт диагностику, данные для M2 и M3 и основу для этапа B.

## Решение

### Этап A — окно по объёму (этот ADR)

**1. Размер окна.** Для каждой пары «площадка × инструмент» вычисляется $V_{cal}=k\cdot\bar q$ в долларах. Окно — число уровней $n$, равное максимуму по двум сторонам стакана из чисел «первый уровень, на котором накопленная стоимость $\sum p_i q_i$ стороны достигла $V_{cal}$». Кривая и все способы снятия наклона считаются по первым $n$ уровням обеих сторон. Последний уровень в расчёте объёма учитывается частично (для диагностики $\delta_n$); в снимок уходят целые уровни.

**2. Средний размер сделки $\bar q$.** По инвариантности из документа: оборот в день $W=\sigma_{day}\cdot V_{\$}$ ($V_\$$ — суточный оборот пары в долларах, $\sigma_{day}$ — дневная волатильность), частота сделок $\mu=\mu^*\,(W/W^*)^{2/3}$ в день, $\bar q=V_\$/(\zeta\mu)$. Константы документа: $\mu^*=85$ сделок в день, $W^*=8\cdot10^{5}$ долларов в день, $\zeta=2$. Для крипты они **не проверены** — это открытый вопрос документа, поэтому все константы задаются конфигом, а для конкретной пары допускается явное значение $\bar q$ (оно перекрывает формулу). Источники входов: $V_\$$ — суточный объём из тикера площадки, умноженный на mid (Binance и Coinbase `venues` уже читает вместе со стаканом; у OKX и Kraken прежний запрос тикера по пути Binance даёт 404 и объём всегда 0, поэтому при запросе окна адаптер берёт настоящий тикер — OKX `/api/v5/market/ticker` (`vol24h`), Kraken `/0/public/Ticker` (`v[1]`) — в отдельное поле `window_volume_24h`, не трогая `volume_24h` и зависящий от него τ-потолок кривой); для пар с котируемой валютой не USDT — ещё на курс этой валюты к USDT на той же площадке (нет курса — окно не применяется, см. п. 6); $\sigma_{day}$ — волатильность пары из таблицы `ce_asset_volatility` (чтение, обновляется сервисом market_data), пересчитанная из «на корень секунды» в дневную умножением на $\sqrt{86400}$.

**3. Множитель $k$.** Один глобальный параметр (`CE_DEPTH_K`, по умолчанию 10), а не по площадкам: подбор $k$ под каждую площадку подменил бы калибровку подгонкой. Пересматривается раз в квартал; изменение — новая версия конфигурации. Условия выбора $k$ из документа (число уровней не меньше 5, кривизна издержек в пределах ±20 %, устойчивость наклона между $k$ и $2k$ в пределах ×1,3) проверяются диагностикой, но автоматически $k$ не подстраивают.

**4. Стабильность.** $V_{cal}$ сглаживается экспоненциально (EWMA, коэффициент 0,2 на снимок). Число уровней $n$ меняется, только если новое значение выходит за ±15 % от текущего (гистерезис), иначе остаётся прежним — окно не должно «дышать» вместе с шумом волатильности.

**5. Запрос глубины.** Чтобы не тянуть 1000 уровней там, где нужно 100, лимит REST-запроса выбирается по предыдущему $n$ с запасом 25 % и округляется вверх до ступени цены запроса площадки (у Binance ступени 100, 500, 1000, 5000; вес запроса растёт со ступенью). Первый запрос после старта идёт на потолке API площадки. Потолки по умолчанию: Binance 1000, OKX 400, Kraken 500, Coinbase — весь стакан (параметра глубины у площадки нет, потолок в конфиге 100 000 не ограничивает), остальные площадки — 100; переопределяются конфигом. После ответа снимок обрезается до $n$ перед публикацией в Kafka и записью в хранилище — клиринг и воспроизведение видят ровно то окно, по которому посчитана кривая.

**6. Ловушки и деградация.** Каждый случай помечается тегом в `VenueLiquidityCurve.meta.tags` и строкой лога:

| Флаг | Когда | Поведение |
| --- | --- | --- |
| `truncated` | сторона не набрала $V_{cal}$, хотя площадка отдала меньше запрошенного (стакан тоньше окна) | берётся весь доступный стакан, экстраполяции нет, доверие к кривой понижено |
| `request_limited` | сторона не набрала $V_{cal}$, а площадка отдала ровно столько, сколько мы запросили (окно обрезал наш собственный лимит) | это не усечение стакана: следующий запрос идёт на потолке API, состояние окна не накапливается на неполных данных |
| `coarse_tick` | $n<5$ (крупный шаг цены, на $V_{cal}$ приходится 1–2 уровня) | кривая считается, доверие понижено |
| `no_inputs` | нет суточного объёма, волатильности или курса котируемой валюты | окно не применяется, используется прежнее `depth_levels` (20) |
| `api_capped` | потолок API меньше нужного $n$ при лимите, уже стоящем на потолке | то же, что `truncated`, причина — лимит площадки |

**7. Диагностика на каждом снимке.** В лог и теги: $\bar q$, $V_{cal}$ (до и после сглаживания), $n$ по сторонам, $\delta_n$ (сдвиг цены в б.п. на объёме $V_{cal}$ с учётом частичного последнего уровня), хордовая оценка $\kappa_{chord}=V_{cal}/\delta_n$ (диагностика жёсткости стакана), флаги.

**8. Переключатель.** `CE_DEPTH_WINDOW_ENABLED` (по умолчанию 0): при 0 поведение и все выходные данные такие же, как до ADR. Включение на dev — отдельное решение владельца.

### Этап B — способ M5: наклон по регрессии издержек прохода (требует решения владельца)

Чтобы окно повлияло на клиринг, нужен оценщик, который использует **всё окно**, а не минимум по верхним уровням. Документ предлагает его в шаге 4: подгонка издержек прохода по стакану $C(Q)=\tfrac{s}{2}|Q|+\tfrac{Q^2}{2\kappa}$ (здесь $Q$ — объём ордера в долларах, $s$ — относительный спред, $\kappa$ — жёсткость стакана: сколько долларов нужно, чтобы сдвинуть цену на единицу её относительного значения). Это пятый способ M5 рядом с M1–M4. Проверка формул (специалист по торговой математике, 2026-10-15) дала:

- **Форма регрессии одна:** $\delta_k=a+b\,D_k$ (сдвиг VWAP против накопленной стоимости) с робастной функцией потерь Хьюбера, обе стороны отдельно; $a=s/2$, $b=1/(2\kappa)$. Веса наблюдений (специалист предлагает $1/Q$) уточняются при реализации; без фиксированной формы результат на нелинейной книге недетерминирован.
- **Конвенции.** Для линейной книги средний сдвиг VWAP равен $s/2+Q/(2\kappa)$, предельный (цена после исполнения) — $s/2+Q/\kappa$. Поле `safe_translator.alpha_ext` и правило R-F05A-008 используют сдвиг VWAP: там $\alpha_{M5}=1/b=2\kappa\cdot10^{-4}$ долларов на б.п. Путь CE в `agent_builder.hpp` использует цену уровня (предельная конвенция) и ‰: там $\alpha_{M5}=\kappa\cdot10^{-3}$ долларов на ‰. Подача одного числа в оба пути смешала бы конвенции (в 2 раза) и единицы (в 10 раз).
- **Безопасность по §6.3** (прямая наклона не выше лестницы точек «сдвиг — глубина», то есть хедж не убыточен по средней цене). При $s>0$ спред уходит в свободный член $a$, и M5 не меньше M4 (на линейной книге с $s=2$ б.п.: M1=M4≈333, M5=400), то есть M5 уже не консервативный минорант. Проверка формул рекомендовала при M5 держать в полке ½ спреда, иначе спред пропадает и из наклона, и из полки; владелец решил иначе (см. «Решение владельца» ниже): полки нет, спред остаётся только в свободном члене подгонки.
- **Агрегация сторон.** Документ говорит «усреднить κ по сторонам», код везде берёт минимум по сторонам; для M5 сохраняется минимум (консервативнее), среднее остаётся в диагностике.
- **Инварианты:** (I1) $b>0$, $a\ge0$, всё конечно, иначе откат на M4 с флагом; (I2) на линейной книге $\kappa$ не зависит от $k$ (разница между $k=3$ и $k=30$ до 1 %), $n(k)$ не убывает; (I3) сверка с хордой — только в одной конвенции: $2\kappa_{regr}\cdot10^{-4}$ против $\alpha_{chord}=V_{cal}/\delta_n$, допуск ±20 % (прямое сравнение $\kappa_{regr}$ с $V_{cal}/\delta_n$ даёт 0,5 на идеальной книге и сработало бы ложно); (I4) $\alpha_{ext}=\min(bid,ask)$; (I5) усечение стакана, $n\le2$ или меньше трёх различных $\delta$ — откат на M4 с флагом; (I6) состояние окна (сглаженное $V_{cal}$, прежнее $n$) воспроизводимо: итоговые $n$ и $V_{cal}$ публикуются в тегах кривой, повторный расчёт их не пересчитывает.
- **Тест T-M5-LIN:** линейная книга $\kappa=2\cdot10^{6}$ долларов, $s=0$, точки $D=2000/10000/20000$ дают $\delta_{VWAP}=5/25/50$ б.п.; ожидается $\alpha_{VWAP}=400$ в каждой точке (M1=M2=M4=M5=400), для CE-пути $\kappa\cdot10^{-4}=200$ долларов на б.п. предельной конвенции; вариант $s=2$ б.п. даёт M5=400 при M1=M4≈333.

**Решение владельца (2026-10-15):** M5 подключается в путь агентов CE (`agent_builder.hpp`), за флагом; множитель $k$ — один на всю сеть, число уровней $n$ — следствие, а не параметр (поэтому $k$ не подбирается под лимиты API, нехватка глубины помечается флагом `truncated`); $\lambda_b$ измеряется регрессией на уровнях окна. Векторная кривая со `slope_method` (1..4) этим решением не меняется: перечисление в контракте, ограничение в БД и сеттер `SetClearingSlopeMethod` остаются прежними.

**Реализация этапа B** (код в ветке, не включён ни на одном стенде). Переменная окружения `CE_ALPHA_METHOD` (4 — по умолчанию, прежний минорант; 5 — M5) читается в `market_data` на каждом окне. M5 считается отдельно для каждой стороны книги по уровням кривой: накопленная стоимость $V_i$ и предельный сдвиг уровня $\delta_i$ (‰, по цене уровня) берутся на равномерной сетке объёма из 32 узлов (`CE_M5_GRID_POINTS`) от нуля до $V_{max}=\min(\text{глубина стороны},V_{cal})$, веса узлов равны; прямая $\delta=a+bV$ подгоняется методом Хьюбера (взвешенные наименьшие квадраты с пересчётом весов, масштаб по медианному абсолютному отклонению, 30 итераций, детерминированно), $\alpha_{side}=1/b$, итог — минимум по сторонам, глубина переводчика $\theta\cdot\alpha_{ext}$. В этой конвенции множитель между $\kappa$ и $\alpha$ не нужен: $\alpha_{CE}=\kappa\cdot10^{-3}$ получается напрямую. $V_{cal}$ в единицах котируемой валюты приходит из тега кривой `depth_window.v_cal_quote`; если тега нет, окном служит вся глубина стороны (M5 работает и на прежних 20 уровнях).

**Отклонения от проверки формул и почему.** Проверка (специалист, 2026-10-15) требовала откатываться на M4 при $a<0$ и при любом усечении стакана. Измерение на 16 подгонках живых стаканов показало: отрицательный свободный член $a$ бывает у выпуклых книг (SOL на Binance, Kraken BTC; 7 из 16), поэтому жёсткий откат убрал бы M5 примерно с половины сторон. Принято: условия отката — число уровней меньше трёх, меньше трёх различных значений сдвига на сетке, наклон $b\le0$, покрытие стороной меньше 50 % $V_{cal}$ (`CE_M5_MIN_COVERAGE`); отрицательный $a$ только помечается (счётчик в логе). Усечение стакана при покрытии 50 % и выше не отменяет M5: окно просто короче, а флаг `truncated` остаётся в теге кривой. Полка при M5 не меньше $m\cdot$ ½ спреда, где $m$ задаётся `CE_M5_HALF_SPREAD_MULT`; **по умолчанию $m=0$ — полки нет** (решение владельца 2026-10-15: пока вычисляем без комиссии и без полки). Спред при этом остаётся только в свободном члене $a$ (диагностика), и из наклона, и из полки он выпадает — это принятое последствие; $m=1$ вернул бы ½ спреда как барьер.

**Главный риск включения — рост потока.** M5 — оценка жёсткости на масштабе сделки, M4 — консервативный минимум по верхним уровням. На живых стаканах 2026-10-15 при $k=10$ M5 даёт глубину в 5–20 раз больше M4 (например, Binance BTC/USDT, продажи: M4 = 369 тыс., M5 = 7 533 тыс. USDT на ‰; Binance ETH/USDT, продажи: 231 тыс. против 1 391 тыс.). Поток клиринга пропорционален глубине, поэтому при той же разнице цен он вырастет на порядок. Диагностика ADR-075 показала, что поток сейчас запускают в основном фантомные базисы от устаревших якорей; M5 без свежих якорей усилит именно их. Поэтому включение M5 на dev — только отдельным решением, после офлайн-сравнения и вместе с контролем возраста якоря.

**Наблюдаемость.** В журнале: `Depth window (ADR-077)` на каждый снимок площадки (количество уровней, $V_{cal}$, $\delta_n$, $\alpha_{chord}$, флаги) и `CE clearing: α по M5 (ADR-077)` на каждый батч (сколько агентов на M5, сколько откатилось на M4, максимум отношения M5 к M4). Вывод этих величин на экран через цепочку «сервис → BFF → фронт» — следующий шаг, в этой работе не сделан.

> **Conflict Note.** Два пути расчёта наклона в репозитории расходятся: векторная кривая (`curve_to_levels.cpp`, читает `slope_method`, сдвиг VWAP, б.п.) и агенты CE (`agent_builder.hpp`, не читает `slope_method`, цена уровня, ‰). Документ R-F05A-008 описывает первый путь, клиринг CE на dev использует второй. Расхождение зафиксировано здесь, а не выбрано молча; разрешается решением владельца по этапу B.

### Вне объёма этого ADR

- Шаг 1 документа (методика оценки среднего размера сделки и среднего капитала агентов) — отдельная методика; здесь использована только формула инвариантности как стартовая оценка с возможностью явного значения.
- Шаг 5 документа ($\lambda_b=\rho\kappa$ — перманентное влияние через скорость восстановления стакана $\rho$, нужна лента сделок) — слой ликвидности $\Lambda,\varphi_i$ из ADR-066 остаётся отложенным.

### Ревью кода (2026-10-15)

Ревью (`code-reviewer`) нашло четыре дефекта, все проявлялись только при включённом окне; исправлены до публикации ветки. (1) У OKX и Kraken окно не применялось бы вовсе: их тикер по пути Binance возвращает 404, объём был 0 — добавлено отдельное поле `window_volume_24h` и настоящий тикер при запросе окна (без окна запрос прежний; тест в `cex_ws_rest_adapter_test.cpp`). (2) Флаг `truncated` ставился и тогда, когда окно обрезал наш собственный лимит запроса: добавлены `request_limited` и принудительный запрос на потолке API; при `no_inputs` состояние окна (сглаженное $V_{cal}$, прежнее $n$) сбрасывается. (3) Обновление кэша волатильности из PG шло под общим мьютексом без таймаута подключения и могло остановить все потоки опроса: теперь обновление вне мьютекса, остальные читают прежний кэш, в строку подключения добавляется `connect_timeout=2`. (4) Потолок Coinbase 1000 ограничивал «весь стакан»: поднят до 100 000. Границы переменных окружения (число уровней, запас, $k$) проверяются.

**Не проверено в ревью и остаётся риском перед включением на dev.** Во-первых, доходят ли до `market_data` все $n$ уровней без передискретизации: уровни CE берутся из сетки кривой (`q_grid` и `p_of_q`), а не из сырого снимка; число точек сетки и сохранность полной глубины надо увидеть в первом прогоне по счётчикам отката M5 по покрытию. Во-вторых, фильтр тонких площадок `CE_MIN_DEPTH_RATIO` (по умолчанию 0,05): он сравнивает глубину агента с максимумом по паре, а M5 растит глубину неравномерно (по замеру у Binance примерно в 20 раз, у Kraken в 3–4 раза), поэтому при M5 фильтр выбросит больше площадок, чем сегодня (например, глубина агента — минимум по сторонам: у Kraken BTC/USDT 195 тыс., у Binance BTC/USDT 5 132 тыс., отношение 3,8 % окажется ниже порога 5 %, тогда как по текущему минорату 67 тыс. к 369 тыс. даёт 18 %).

## Альтернативы

- Оставить 20 уровней и подбирать способ M1–M4. — отклонено: способы M1 и M4 определяются верхом стакана, любое число уровней вне верха их не меняет; кривая остаётся калибровкой не на том масштабе.
- Увеличить фиксированное число до 100 или 500 уровней для всех. — отклонено: для Kraken этого много (нужно ≈ 100–200), для Binance BTC мало; число уровней не связано с размером сделки, а лишняя глубина удорожает запрос и хранение.
- Подбирать $k$ отдельно под каждую площадку. — отклонено: подгонка скрывает различия площадок, которые калибровка должна показывать; документ требует одно глобальное $k$.
- Брать окно из быстрой полосы ADR-070. — отклонено: быстрая полоса работает по запросу фронта, до 8 пар, с отдельным лимитом; цикл клиринга должен получать окно сам и всегда.
- Экстраполировать стакан, если его не хватает до $V_{cal}$. — отклонено: документ прямо запрещает (флаг `truncated`), экстраполяция выдумывает ликвидность.

## Последствия

**Положительные.**

- Кривая ликвидности отражает масштаб реальной сделки, а не верх стакана; окно объяснимо (объём, а не магическое число) и воспроизводимо (флаги и теги в каждой кривой).
- Деградация явная: тонкий стакан, крупный шаг цены и урезанный API не маскируются под нормальный результат.
- Поведение при выключенном переключателе не меняется.

**Отрицательные.**

- Рост полезной нагрузки: снимок Binance BTC/USDT вырастает с 20 до сотен уровней; растёт вес REST-запросов (у Binance запрос на 1000 уровней стоит 50 единиц веса против 5 у запроса на 20), размер сообщения в Kafka и объём записи в `venue_snapshots`. Это нужно измерить на dev до включения; смягчение — адаптивный лимит запроса (п. 5).
- Константы документа не проверены на крипте, а $\bar q$ дрейфует вместе с волатильностью; результат зависит от сглаживания (п. 4) и требует наблюдения.
- Эффект на клиринг измерен: окно меняет M2 и M3 в разы, но глубина переводчика CE (минимум по верхним уровням) остаётся прежней на всех парах, кроме Binance BTC/USDT; без этапа B включение этапа A добавляет нагрузку (запросы, хранение), почти не меняя клиринг.
- Совместимость со свежестью данных (ADR-075): запрос глубины дороже, значит, цикл по парам медленнее; окно и частота опроса надо рассматривать вместе.

## Обратимость

Полностью обратимо переключателем `CE_DEPTH_WINDOW_ENABLED=0` и перезапуском `venues`: возвращается прежний путь (`depth_levels` из конфига площадки, лимит запроса `lob_max_levels`). Схемы хранилищ не меняются; новые теги кривой — необязательные поля `meta.tags`. После приёмки на dev (наблюдение за долей усечённых окон, весом запросов и качеством потока) значения $k$ и констант фиксируются в версионируемой конфигурации.
