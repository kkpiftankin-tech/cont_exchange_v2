# ADR-086 — Двухосевая маршрутизация реплик, V-петля, отмена единого сэндвича

> **Статус: accepted (2026-10-27).** Принято по поручению владельца
> («Откорректируйте структуру проекта с учётом данных в прикреплённом
> файле», документ зарегистрирован как [IN-019](../../../incoming-docs/IN-019.meta.md))
> для Этапа 0 десятиэтапного плана внедрения. Этапы 1–9 плана **не приняты
> этим ADR** — каждый требует отдельного подтверждения владельца перед
> исполнением (см. `IN-019.meta.md`, инструкция документа §0).

## Контекст

**Что было.** Единственный канонический процесс разработки фичи
(`docs/00-methodology/feature-development-process.md`,
`ingest-and-agents-integration.md`) описывал один путь для любого изменения:
14-уровневый сэндвич `ingress(open) → agent(refine) → ingress(close)`,
где `docs-ingestion-engineer` — единственный писатель в `docs/` на каждом
уровне, а `sdlc-coordinator` — навигатор, с которого «начинать» разбор
любой задачи. Для полной новой фичи это оправдано. Для короткой реплики
владельца («что за число в колонке „базис“?», «подпись оси неверная») —
избыточно: нет маршрута короче полного прохода по 14 уровням, что на
практике приводит либо к пропуску процесса целиком (путь «ни одного
агента»), либо к его формальному обходу.

Этот разрыв уже частично закрывался без ADR: `.claude/rules/agent-routing.md`
(классы S/M/L/XL + триггеры эскалации, принято без отдельного ADR 2026-09-28)
и `.claude/skills/triage/` — рабочие, но не согласованы явно с каноническим
документом процесса, который сэндвич всё ещё описывает как единственный путь.

**Источник решения.** [IN-019](../../../incoming-docs/IN-019.meta.md) —
инструкция «Двухосевая маршрутизация реплик, V-петля „спецификация —
проверка“ и согласованность проекта» (v2, 2026-10-26): ось Ф (где в
продукте: `F-XX → CAP-FXX-NN → UC-FXX-NN → UI-…`), ось Р (на каком уровне
спецификации: Р1…Р15, левая ветвь — спецификация и код, правая —
проверка), класс изменения (S/M/L/XL/spike) выводится из множества
затронутых уровней Р, а не назначается заранее. Полная модель — в самом
документе; здесь фиксируется только решение и его объём.

## Решение

1. **Единый сэндвич `ingress(open) → agent(refine) → ingress(close)` как
   обязательный путь для любого изменения — отменяется.** `docs-ingestion-
   engineer` перестаёт быть единственным писателем `docs/` на каждом
   уровне жизненного цикла. За ним остаётся прежняя, более узкая роль:
   приём и регистрация входящих документов (`incoming-docs/` → `IN-NNN`)
   — это не отменяется, а сужается.
2. **Принимается модель из IN-019 как целевая**: ось Ф, ось Р (Р1…Р15),
   V-петля (спуск по затронутым уровням спецификации, затем проверка
   каждого затронутого уровня), три класса артефактов (нормативные —
   блокируют; поясняющие — несут `verified:`; генерируемые — не
   редактируются руками), карточка изменения CR для M/L/XL, git-трейлер
   `Change: S|spike` для лёгких изменений.
3. **Внедрение — поэтапное, десять этапов (IN-019 §8), каждый со своим
   PR и отдельным подтверждением владельца перед началом** — не одним
   изменением. Этим ADR принимается только Этап 0 (этот документ и его
   соседи по плану). Статус остальных этапов — `not started`, см.
   `IN-019.fragment-map.md`, пункт 20.
4. **До завершения Этапа 5** (новый маршрутизатор `route.py`, навык
   `change`, правило `change-routing.md`) **триггеры и классы S/M/L/XL из
   `.claude/rules/agent-routing.md` продолжают действовать без изменений**
   — IN-019 сам явно это оговаривает (§3.6: «Триггеры эскалации текущего
   agent-routing.md §2 сохраняются поверх класса»). `agent-routing.md` не
   удаляется и не заменяется этим ADR.
5. **Три пункта модели IN-019 пересекаются с уже существующими
   механизмами проекта и требуют отдельного явного решения на
   соответствующем этапе** (не молчаливой замены или задвоения):
   - `change-routing.md` против `agent-routing.md` — решение на Этапе 5;
   - карточка `CR-*.md` против уже работающего `docs/feedback/FB-*.md` —
     решение на Этапе 4;
   - `tools/consistency/check.py` (правила C-01…C-17) против уже
     существующих `traceability-checker`, `feature-yaml-checker`,
     `in013-checker`, `link-audit.py`, `docs-code-drift` — решение на
     Этапе 2.

## Альтернативы

- **Оставить единый сэндвич, не вводить ось Р.** Отклонено: не даёт
  короткого маршрута для реплик уровня «вопрос»/«мелкая правка», что и
  было поводом к IN-019.
- **Принять всю модель IN-019 и все 10 этапов одним ADR и одним PR.**
  Отклонено: план больших изменений (новый реестр, маршрутизатор, ревизия
  16 агентов, CI-гейты) без промежуточной проверки противоречит собственным
  принципам документа (P-09 «маленькие изменения», P-13 «гейт с правом
  исключения») и его же явной инструкции исполнять этап за этапом с
  подтверждением.
- **Внедрить `route.py`/`change-routing.md` сразу, не дожидаясь Этапа 5.**
  Отклонено: эти механизмы не существуют до Этапа 5; ссылка на них до
  появления — битая ссылка, что поймал бы `link-audit.py`.

## Последствия

- Канонический документ процесса (`feature-development-process.md`)
  переписывается под новую модель как целевую, с явной пометкой, что уже
  работает сегодня, а что — план (следующие пункты Этапа 0).
- `ingest-and-agents-integration.md` помечается `superseded by ADR-086`,
  остаётся только описание приёма входящих документов.
- `.claude/skills/ingest-docs/SKILL.md` теряет раздел «Agent Integration
  (per-level sandwich)» — сам 9-шаговый pipeline (Register…Generate tasks)
  не меняется.
- `docs/00-methodology/agents.md` обновляется: факт расположения агентов
  (`.claude/agents/*.md`, не «вне репозитория») и таблица уровней Р вместо
  таблицы «этап SDLC → агент».
- Старые ссылки на сэндвич-модель как единственный путь, оставшиеся в
  других документах, становятся историческими упоминаниями отменённого
  процесса, не текущей инструкцией — поиск и пометка таких мест (кроме
  явно помеченных `superseded`) — отдельная задача Этапа 1 (приёмка Этапа
  0: `grep -rE "сэндвич|ingress\(close\)|writer-of-record" docs .claude`
  находит только superseded-документы и этот ADR).

## Обратимость

Высокая. Ничего не удаляется безвозвратно: `ingest-and-agents-integration.md`
помечается `superseded`, не удаляется; `agent-routing.md` не трогается;
содержимое старого `feature-development-process.md` остаётся в истории git.
Откат — новый ADR, меняющий статус этого на `superseded`, и возврат
документов к прежней редакции из истории. Этапы 1–9 плана IN-019 ещё не
начаты и могут быть скорректированы или не исполнены вовсе без отмены
этого решения — ADR фиксирует только модель и порядок Этапа 0.
