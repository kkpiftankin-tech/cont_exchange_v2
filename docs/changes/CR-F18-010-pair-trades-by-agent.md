## Реплика

Владелец, 2026-10-28: «На панели PnL в окне Сделки на внешних биржах по парам — объём и цены — нужна возможность отображать графики для конкретного агента».

## Runtime (для реплик по экрану)

Блок показывал сделки всех агентов вместе. Агент выбирался только для графика «Заработок во времени» (клик по строке таблицы «Заработок агентов»); блок пар этого выбора не знал. Идентификаторы агентов в таблице (`T_BTC_binance`, `A_BTC_binanceokx`, `T_ETH_BTC_okx` …) совпадают с сегментом агента в `child_orders.hedge_flow_id` (`ce|band|<агент>|<актив>|<биржа>`): проверено на dev по 7 суткам.

## Решение (по умолчанию, без вопросов владельцу)

- Выбор агента — тот же, что для графика заработка: клик по строке таблицы (повторный клик снимает). Один выбор управляет обоими графиками вкладки; в блоке пар виден значок «агент: <имя>» с кнопкой «все агенты» и, пока агент не выбран, подсказка, как его выбрать.
- Маршрут `GET /api/vector-clearing/pair-trades-history` получает необязательный параметр `agent` и возвращает его эхом (`agent`); формат проверяется (латиница, цифры, `_ . -`, до 64 знаков, иначе 400). SQL фильтрует по `split_part(hedge_flow_id, '|', 3)`, значение передаётся параметром запроса.
- Справочник пар `known_pairs` и его кэш считаются по агенту: у неактивной пары дата «последняя сделка» — дата хеджа этого агента, а не системы.
- Выбор пар запоминается отдельно для каждого агента (ключ `pnl.pairs.selected.<агент>`), общий выбор не затрагивается.
- Агент без хеджей (например, `A_USDT_*`) — пустой график с пояснением, не ошибка.
- Нагрузка: комбинаций (окно × агент) много, поэтому кэш до 24 записей с вытеснением давно не обновлявшихся (LRU), для запросов по агенту — не больше 4 одновременных тяжёлых запросов (основной и справочник пар вместе; пул PostgreSQL BFF — 5 соединений на все маршруты): сверх — прежний просроченный ответ того же агента либо 503 `pair_trades_busy`; режим «все агенты» предел не режет. Ответ с недополученным справочником пар кэшируется 3 с, а не 30.
- Смена агента убирает графики и пары прежнего агента сразу (смена окна по-прежнему оставляет прежний график приглушённым); прежний BFF без поля `agent` даёт пояснение «обновите frontend-api» вместо чужих данных. Порядок выкладки: frontend-api, затем frontend-web.
- ADR не требуется: необязательный параметр внутреннего BFF-маршрута, ответ для прежнего клиента тот же (кроме `agent: null`), схемы, границы сервисов и денежная модель не меняются; прецедент CR-F18-006…009.
- Формулы, интервалы и комиссия не меняются: расчёт идёт по отфильтрованным строкам.
