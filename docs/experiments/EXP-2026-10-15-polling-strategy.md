# EXP-2026-10-15-polling-strategy

**О прогоне.** Как часто и как надёжно опрашивать все четыре биржи сразу,
чтобы цена, на которой принимается торговое решение, была стабильно
свежей — даже если одна из бирж в этот момент сбоит. Окно 2026-10-15
≈12:00–15:30 UTC: замеры на живом dev + расчётная модель с восемью
случайными повторами на сценарий (для устойчивости выводов). Итог оформлен
как принятое архитектурное решение (ADR-078); этот прогон — доказательная
база для него.

**Вопрос, с которым пришёл владелец.** Нужен стабильный период обновления
цен по всем биржам и понятный план действий при сбое опроса одной из
них — с минимальными потерями и в данных, и в вычислительной нагрузке;
выбрать самый эффективный способ с учётом особенностей конкретных бирж.

## 1. Что не так в текущей схеме опроса (измерено на dev)

| Наблюдение | Что показали данные |
| --- | --- |
| Период обновления нестабилен | Фактический интервал между обновлениями — от 9 до 13 секунд в 90 % случаев, у Kraken — до 20 секунд |
| Последняя в очереди пара страдает сильнее всех | Если лимит запросов исчерпан, система просто пропускает оставшиеся пары, а не ждёт; одна из пар на Kraken получила лишь ≈61 % возможных обновлений за полтора часа, её цена устаревала до 35 секунд |
| Сбой по одной паре блокирует всю биржу | Защитный механизм общий на всю биржу: несколько ошибок подряд по ОДНОЙ паре временно отключают опрос ВСЕХ пар этой биржи — Coinbase из-за эпизодических ошибок на паре получил только 55–66 % возможных обновлений за полтора часа |
| Сбой теряет целый цикл обновления, а не только одну попытку | Нет повторной попытки внутри того же цикла — неудача означает ожидание следующего полного цикла, и задержка удваивается |
| Расчёт и запись в базу идут в том же потоке, что опрос | Построение кривой занимает ≈70–107 мс на снимок, запись в базу — синхронная |
| Данные не подменяются незаметно устаревшими | За полтора часа **ни разу** не было случая, чтобы устаревшая книга заявок выдавалась потребителю как свежая — потери честные (пропущенное обновление), не скрытые (подмена) |

Задержка одного запроса (типичная, с переиспользованием соединения):
Binance 285 мс, OKX 330 мс, Kraken 55 мс, Coinbase 50 мс.

## 2. Как проверялось: модель + живые данные

Построена модель с явными допущениями (официальные лимиты бирж, форма
хвоста задержек, сценарии сбоев) и измеренными величинами (задержки запроса
выше). Модель служит для **сравнения способов опроса между собой**, не для
предсказания абсолютных цифр на проде — её базовый сценарий (как сейчас)
проверен на согласие с реальностью: модель даёт период ≈7,4 с, живой dev —
≈9 с; голодание последней пары на Kraken модель тоже воспроизводит.

**Проверялись сценарии:** обычная работа; эпизодические сбои одной биржи
(как при отсутствующем заголовке запроса); короткий всплеск массовых
таймаутов по всем биржам; Kraken оказывается строже по лимиту, чем
считалось; авария одной биржи на полторы минуты; и всё это одновременно.

**Сравнивались три способа опроса:** «как сейчас» (без изменений); новый
способ по расписанию — фиксированный период для каждой пары, несколько
параллельных попыток на биржу, ограничение нагрузки по бюджету, таймаут на
попытку, повтор внутри одного цикла, изоляция сбоя только по конкретной
паре, а не по всей бирже, автоматическое замедление при отказе по лимиту
(это и есть решение, принятое как ADR-078); и потоковое соединение
(WebSocket) — для сравнения, смоделировано упрощённо, не измерено на
практике в этом прогоне.

**Что измерялось:** как часто обновляется цена пары и насколько стабильно
это происходит; насколько свежей видит цену потребитель в произвольный
момент (и какая доля времени цена старше 15 секунд — то есть прямая
информационная потеря для торгового решения); вычислительная нагрузка;
нагрузка запросами на биржу; число отказов по лимиту (риск получить
блокировку); и как быстро система приходит в норму после аварии биржи.

## 3. Результаты (сокращённо — полные таблицы по всем сценариям в техническом блоке внизу)

В обычных условиях новый способ (по расписанию) против текущего: период
обновления стабильнее (разброс «худший случай / типичный» ≈1,2 против
1,5–2,2), худший случай свежести цены ≈3 секунды против ≈9,6 секунды. У
Kraken, самой слабой по лимитам биржи, доля времени с устаревшей (>15 с)
ценой падает с 20,9 % до 0 %. При сбоях (эпизодические ошибки, всплеск
таймаутов, авария биржи) преимущество нового способа сохраняется и местами
увеличивается — например, при всплеске таймаутов худший случай свежести
цены на Binance: 3,3 секунды против 28,9 секунды у текущей схемы.

Цена этого улучшения: вычислительная нагрузка (построение кривой) растёт
примерно в 2,5 раза, нагрузка запросами на биржи — примерно до 10 % от
лимита Binance (запас большой). Авария биржи всё равно даёт потерю
свежести данных на время самой аварии при любом способе опроса (кроме
потокового соединения) — разница в том, как быстро система восстанавливает
нормальную частоту обновлений после аварии: 5,8 секунды у нового способа
против 7,1 секунды у текущего.

## 4. Как подбирался конкретный период обновления

Для быстрых по лимитам бирж (Binance, OKX) перебирались период обновления
(2, 3 или 5 секунд) и таймаут одной попытки (0,8 или 1,5 секунды). При
периоде 2 секунды запросы одной биржи почти постоянно заняты, и очередь
сама растягивает фактический период; при длинном таймауте (1,5 с) повторная
попытка не успевает поместиться в тот же цикл. **Период 3 секунды с
таймаутом попытки 0,8 секунды — лучший баланс между стабильностью периода и
свежестью данных**; период 5 секунд даёт чуть более ровный интервал, но
заметно хуже по свежести.

## 5. Что исправлено по ходу построения модели (не итоговые выводы, а уроки процесса)

1. Первая версия модели считала сбой сети «поломкой конкретной пары» —
   из-за этого при аварии биржи каждая пара отдельно уходила в карантин, и
   восстановление после аварии в модели занимало вчетверо дольше, чем
   показывает реальная система. Исправлено: сбой сети относится ко всей
   бирже целиком, а не к отдельной паре.
2. Одной повторной попытки мало для быстрых бирж: у Coinbase один запрос
   занимает 50 мс, в один цикл помещается несколько попыток — с тремя
   повторами эпизодические ошибки почти перестают быть заметны (худший
   случай свежести данных падает с 20,5 до 3,7 секунды).
3. Карантин после трёх ошибок подряд излишне наказывает пары с частыми, но
   не критичными сбоями (такая пара всё равно успешно отдаёт 60 % запросов)
   — карантин после пяти неудач, уже после исчерпания повторов, этого
   избегает.

## 6. Выводы

- Фиксированный период обновления для каждой пары, со сдвигом по фазе между
  парами, даёт заметно более стабильную и свежую цену, чем текущая схема —
  особенно у самой слабой по лимитам биржи (Kraken): доля времени с
  устаревшей ценой падает с 20,9 % до 0 %.
- Устойчивость к сбоям обеспечивает не «опрашивать чаще», а правильная
  изоляция проблемы (конкретная пара или конкретная биржа, не всё сразу) и
  повторная попытка в пределах того же цикла.
- Цена устойчивости — более высокая вычислительная нагрузка (построение
  кривой) и чуть более высокая нагрузка запросами на биржи (всё ещё
  далеко от лимитов).
- Авария биржи всегда даёт временную потерю свежести данных на время самой
  аварии — это неизбежно при опросе запросами; радикально снимает проблему
  только переход на потоковое соединение (WebSocket), которое для этого
  прогона смоделировано, но не измерено на практике.
- Kraken остаётся самой слабой по лимитам биржей среди четырёх — для неё
  потоковое соединение даёт наибольший выигрыш в перспективе.

**Вопросы для эксперта по трейдингу.** Нет — это чисто инженерное решение о
надёжности и частоте обновления рыночных данных, решение по нему владелец
уже принял (ADR-078), концептуальных вопросов о торговой стратегии не
возникло.
