# F-18 (v2) — CE: виртуальные контрагенты биржи, позиция агента с нуля и хедж по полосе

> **F-18 эволюционирует**, а не заводится заново. v1 (ADR-054): «капитал CE → чистая позиция →
> хедж от Δпозиции» с target. v2: биржа — **дилер**, её книга — виртуальные контрагенты-агенты
> (переводчики + арбитражёры); позиция агента знаковая, **с нуля**; хедж только при `|c|>q`
> (полоса); прибыль на house; **target отсутствует**, `Z_a = владение(t) − владение(0)`.

Сверено с **фактическим HEAD `d4900700`** (не с `1e8bf6f` из интеграционного плана). Наш HEAD
собирается; у нас есть собственное клиринговое ядро `ce_agent_clearing` (active-set Newton), а
не Engine B/OSQP, на который опирался интеграционный план. Поэтому его Э0 («починить сборку,
достать `pi`, флаг `two_sided`») для нас во многом **неактуален**: у Newton-движка узловые
потенциалы `x` = `π` уже доступны, `ce.position.delta` публикуется.

## 0. Цель

Перевести CE на модель v2: агенты — только **переводчики** (quote, на площадке) и
**арбитражёры** (transfer, между площадками); позиция агента — накопленный неисполненный поток
`c←c+f`, старт **с нуля**, знаковая; наружу только при `|c|>q` (полоса); прибыль на **house**
(невязка, не агент); `Z_a = владение(t) − владение(0)`. Ни склада (STOCK), ни цели (target), ни
book-узла.

## 2. Решения владельца ДО начала (ADR-развилки)

1. **Номер фичи**: F-19 (закрыть пропуск) или F-21.
2. **Номера ADR**: следующий свободный — **ADR-061**; но ADR-050…053 цитируются и отсутствуют в
   репо — подтвердить, не заняты ли они вне репозитория.
3. **Сведение движков**: у нас три пути клиринга — `ce_agent_clearing` (наш, Newton), Engine B
   (`vector_qp_solver`/OSQP, F-05A), Engine A (`ContinuousClearingSolver`, двигает деньги в
   `batch.outputs`). **Рекомендация:** консолидировать v2 на `ce_agent_clearing` (ближе к v2,
   уже сверен с Python-эталоном 1e-9); Engine B — общий fallback (V×A > квадрата), Engine A —
   отдельный вопрос (внутренний FOB-стакан). Требует ADR «сведение движков».
4. **Тип участника**: агенты — **третий тип `AGENT`** (дилерский инвентарь), рядом с
   CLIENT/HOUSE, а не подтип клиента (см. §6).

## 5. Этапы (флаги, все по умолчанию OFF; порядок не переставляется)

- **Э1 — упростить граф до v2 (venue-only + house).** Убрать STOCK-ноги и book-узел из
  `ce_graph_assembler`; добавить house-столбец (единственная ненулевая клетка в узле нумерария —
  восстанавливает ядро, забирает арб-прибыль). A2 → `σ*=m+ρ·c`. Флаг `CE_V2_GRAPH`. Тесты:
  ранг `W=V·A−1`, ядро `(V−1)(A−1)`, `det W_нат=(p₂−p₁)/1000`, house восстанавливает ядро.
- **Э2 — позиция агента с нуля, знаковая, per-agent, в PG.** `CePositionDeltaBatch` → `AgentDelta`;
  `ledger` копит `ce_agent_position(agent_id, asset, venue)` (signed), персист в PG; тип
  участника AGENT (резерв-чек не применяется). Новый RPC `GetAgentPositions`. Флаг `CE_AGENT_POS`.
- **Э3 — полоса ±q и эмиссия.** Наружу только при `|c|>q`; эмиссия уменьшает `c` на отправленное;
  размер по стоимости (`qty←излишек·1000/walk(qty)`, 2-3 итерации); две полосы (переводчик/
  арбитражёр, разный смысл). Флаг `CE_AGENT_BAND`. Тест: после эмиссии `|c|≤q` точно.
- **Э4 — A8 возврат остатка + признание прибыли.** Таймаут возвращает неисполненное в позицию по
  **плановой** цене; прибыль признаётся по факту расчёта (не клиринга); удалить `CE_HEDGE_COOLDOWN_MS`.
  Флаг `CE_AGENT_A8`.
- **Э5 — арбитражёр и перевозы (только симулятор F-20).** Сущность/таблица/топик перевоза; учёт
  «в пути»; проверка `q ≤ остаток узла`. Флаг `CE_TRANSFER_AGENT`. Боевой режим — после отдельного ревью.

## 6. Модель типа участника (AGENT)

`party_type ∈ {CLIENT, HOUSE, AGENT}` в `ledger` — сиблинг, не подтип клиента:

| | CLIENT | HOUSE | AGENT |
|---|---|---|---|
| позиция | ≥0, резерв-чек | капитал/невязка | **знаковая, без резерва** |
| смысл | владение | капитал+арб-прибыль | накопленное обещание клиринга |
| ключ | `(user, symbol)` | `(currency)` | `(agent_id, asset@venue)` |
| двигает владение | сделка клиента | исполнение | **нет** |
| эмиссия | — | — | при `\|c\|>q` |
| лимит | маржа/notional | — | полоса `±q` + остаток узла |

Переиспользуем субстрат счетов/позиций/риск-хуков/разрез по узлам; клиентский контракт
(FlowOrder, резерв, неотрицательность) применяется **по типу**, только к CLIENT. Экономика:
агенты — **дилерский инвентарь биржи** (принципал), клиенты — потребители ликвидности.

## 9. Риски (из интеграционного плана + наши)

- Не начинать с полосы без Э1-Э2 (односторонний поток + полоса ухудшают результат).
- Не выкидывать старый путь — флаги + золотые тесты на одной площадке.
- Полосу не переносить в `matching` (§10.3 — риск-решения в `risk`).
- Граница денег: `σ,α,c,π,невязка` — `double` (диагностика); поток на выходе — `Decimal`.
- Клиринг записал ≠ исполнено (в прототипе разрыв до 6611 USD/1200 тактов) — прибыль по факту.
- Полоса окупается только при встречном клиентском потоке; на чистом стенде её метрики
  отрицательны — это правильно, не ошибка настройки.
- Ловушки процесса: `docs-code-drift.yml` роняет PR без парного изменения docs/specs;
  `F-18/F-20` не в `feature-component-map.yaml`; `.env-example` переобещает флаги
  (`CE_TARGET_*`, `CE_MAX_AGGREGATE_NOP`) — вычистить.
