# F-18 — Поэтапное устранение замечаний (заработок CE-агентов)

Источник — экспертный разбор ветки `feat/F-18-ce-treasury-nop` (HEAD `02eafef`).
Экранный заработок агентов сейчас задают не их стратегии, а дефекты среды и
учёта. План делает результат измеримым, снимает три главные причины и только
потом калибрует. Порядок этапов — по стоимости ошибки (сначала учёт/среда,
потом экономика).

## Шесть причин (из разбора)

| № | Причина | Главная? | Этап-лекарство |
|---|---|---|---|
| 1 | Исполнение «смотрит назад»: хедж матчится о публичные принты минутной давности (REST-пачки, живут 3·T_read≈2мин) | **да** | Этап 3 |
| 2 | Якоря из снимков разного возраста → кажущийся базис > полки → поток по шуму устаревания | **да** | Этап 4 |
| 3 | Арбитражёр удваивает межбиржевую сделку: ноги торгуют в ту же сторону, что переводчики → W·c≠0 | **да** | Этап 2 |
| 4 | Экран ≠ истинный P&L: R по устаревшим мидам; MTM реальных остатков не считается нигде | нет | Этап 1 |
| 5 | Без клиентов доход только из реального базиса; комиссии не моделируются | нет | Этап 5 |
| 6 | Эксперименты несравнимы: метрика переопределялась 5× за 10 дней, флаги вне git | нет | Этап 0 |

## Подтверждение на живых данных dev (2026-10-12, этап 0, read-only)

- **Причина 1 — ПОДТВЕРЖДЕНА.** `oldest_crossing_print_before_emit_s` = **230–352 с**
  у каждого агента (T_ETH_okx 324с, T_SOL_okx 343с, A_ETH_binanceokx 310с…).
  Band-хеджи исполняются о принты, сделанные за 4–6 минут ДО эмиссии.
- **Причина 3 — ПОДТВЕРЖДЕНА.** net_buy переводчиков и арбитражёров на одной
  площадке **одного знака и почти равны** (okx 14:00 T −1.704 / A −1.704;
  binance 14:00 T +1.382 / A +1.239). Каждая межбиржевая сделка исполняется дважды.
- **Причина 3 (ранее, по позициям)** — ноги арбитражёра не противоположны
  (A_BTC_coinbaseokx обе «+»), узловой баланс W·c≠0.

SQL-проверки — в разборе (раздел «Быстрые проверки на dev»); закреплены как
регрессия этапа 0.

## Этапы

Этапы 2–4 независимы (можно параллельно после 0–1). Каждый этап закрывается
числовыми воротами на dev + сдвигом в цифровом двойнике (регрессия на настоящем
коде клиринга).

### Этап 0 — Остановить калибровку, зафиксировать базу
- **Задачи:** dev-профиль (флаги/env) → git; история `f05a_clearing_config` с
  `config_version`; журнал прогонов (run_id, SHA, окно); запись снимков/принтов
  с **биржевым временем** в ClickHouse для replay; генератор выжимки; быстрые
  SQL-проверки причин 1 и 3 (сделано).
- **Ворота:** прогон восстанавливается по run_id; причины 1 и 3 подтверждены (✓).
- **Агенты:** `devops-engineer`, `data-schema-designer`, главный диалог (SQL).
- **Класс:** L.

### Этап 1 — Закрытый учёт (причина 4)
- **Задачи:** System P&L = **MTM реальных остатков**; разложение по агентам
  (тариф/A-исполнение/перенос/комиссии); тесты инвариантов **W·c=0**,
  `c+in_flight=I−F`, `Σ P&L агентов+дом = P&L системы`; экранные формы Ф1–Ф3.
- **Ворота:** за 24ч сумма слагаемых = MTM до 0.01 USDT; тест W·c «красный»
  ровно для ног арбитражёров (до этапа 2).
- **Docs:** `CALC-CE-SYSTEM-PNL` (новый).
- **Агенты:** `trading-domain-specialist`, `test-architect`, `frontend-architect`,
  `data-schema-designer`.
- **Класс:** L.

### Этап 2 — Арбитражёр без рыночного хеджа (причина 3)
- **Задачи:** арбитражёр НЕ эмитит рыночный хедж; его позиция = дисбаланс
  остатков между площадками; заработок = тариф перевоза + изменение базиса;
  включить сдвиг γ_A>0 (разворот потока); физический перевод актива (срок,
  тариф) — отдельной фичей.
- **Код:** `ce_position_projection.hpp`, `ledger_uc.cpp` (band-путь арбитражёра),
  `ce_graph_assembler.hpp`.
- **Ворота:** W·c=0 каждый такт; объём хеджей на площадке = объёму переводчиков;
  нетто системы по активу ≈0; corr(P&L арбитражёра, ΔP_BTC)≈0.
- **Docs:** **ADR-073** (супершидит ADR-069 «две ноги хеджа» и ADR-065 Q2).
- **Агенты:** `solution-architect`, `trading-domain-specialist`,
  `proto-contract-designer`, `code-reviewer`.
- **Класс:** L.

### Этап 3 — Честный симулятор исполнения (причина 1)
- **Задачи:** реализовать **ADR-072 §B** (принят, не сделан): только принты с
  биржевым временем **после эмиссии** + задержка; тейкер = проход по текущему
  снимку книги; maker = резидентная заявка с долей очереди π; комиссии
  maker/taker; мид и F_0 фиксируются на эмиссии и на филле; принт расходуется
  один раз.
- **Код:** `cpp/venues/.../cex_ws_rest_adapter.cpp`.
- **Ворота:** тест «случайной стратегии» даёт P&L/оборот = −(полуспред+комиссия)
  в 95% ДИ; проскальзывание тейкера к миду ≤0 на всех площадках; ноль филлов по
  принту старше эмиссии.
- **Docs:** **ADR-074** (реализация/расширение ADR-072 §B).
- **Агенты:** `trading-domain-specialist`, `cpp-service-architect`,
  `test-architect`, `code-reviewer`.
- **Класс:** L.

### Этап 4 — Синхронные данные (причина 2)
- **Задачи:** биржевое время в снимках; якорь только из снимков не старше
  допуска; полка, растущая с возрастом `c_v ≥ k·σ·√возраст`; WebSocket/учащённый
  опрос основных пар.
- **Код:** `market_data_uc.cpp`, `agent_builder.hpp`; данные — ClickHouse снимки.
- **Ворота:** p90 разности возрастов якорей ≤ допуска (сессия 2 с экспертом);
  доля фантомного потока <10%.
- **Docs:** **ADR-075** (расширяет ADR-070).
- **Агенты:** `data-schema-designer`, `trading-domain-specialist`,
  `devops-engineer`.
- **Класс:** L.

### Этап 5 — Экономика режима «без клиентов» (причина 5)
- **Задачи:** на ≥2 неделях записанных данных при честном исполнении измерить
  захват истинного базиса пар против комиссий; решить: какие пары торговать,
  нужен ли перевод/резидентные заявки — или режим не окупается.
- **Ворота:** P&L/оборот > 0 вне выборки (95% ДИ) — либо осознанное решение не
  торговать в этом режиме.
- **Агенты:** `trading-domain-specialist`.
- **Класс:** L.

### Этап 6 — Калибровка (причина 6 закрыта этапом 0)
- **Задачи:** сетка γ_s × z × K на воспроизводимых прогонах, по символам
  (γ_s∝σ/√Λ, IN-017); Парето «P&L vs max|позиции|» с ДИ; число окон по формуле
  `n≈2(1.96·σ_w/Δ)²` (σ_w≈31 USDT/4-мин окно ⇒ ~74 окна/вариант).
- **Ворота:** выбранная точка лучше базы вне выборки.
- **Агенты:** `trading-domain-specialist`.
- **Класс:** L.

## Артефакты для эксперта (обязательно на каждом этапе)

Каждый прогон этапа порождает **сжатую выжимку** в
[`docs/experiments/`](../experiments/README.md) (ключевые числа + вывод, текста
мало) и строку в `journal.md`. Выжимка генерируется скриптом из журнала прогона
(этап 0), не вручную; руками — только раздел «Вывод». Это основной канал
коммуникации с экспертом-трейдером (сессии 1–6 разбора).
