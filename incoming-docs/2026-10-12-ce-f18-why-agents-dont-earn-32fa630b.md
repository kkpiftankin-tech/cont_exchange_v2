> и как чинить вместе с экспертом.pdf`). Авто-архив не берёт бинарные PDF —
> сохранён вручную (прецедент IN-017). Текст воспроизведён с 15 страниц.

Заработок агентов на экране сейчас задают не их стратегии, а три дефекта среды и
учёта: хеджи исполняются по публичным сделкам минутной давности, якоря площадок
берутся из снимков стаканов разного возраста, а арбитражёр хеджирует обе ноги в
ту же сторону, что и переводчики, и удваивает межбиржевую сделку. Пока они не
устранены, калибровка сдвига цены, полосы и гейтов подбирает параметры под шум.
Ниже — доказательства по коду ветки `feat/F-18-ce-treasury-nop` (HEAD 02eafef),
цифровой двойник на настоящем клиринге, план работы с экспертом и поэтапное
устранение с проверкой каждого шага.

## Диагноз: шесть причин, три из них главные

Причины 1–3 делают экранный заработок артефактом симулятора и данных, причины
4–6 не дают это увидеть.

## Переводчики: из чего состоит «заработок»

Разложение одного филла:
s(p_f − F_0^экр) = A: s(p_f − m_v) [исполнение] + B: s(m_v − F̄) [истинный базис]
+ C: s(F̄ − F_0^экр) [ошибка F_0]. s=+1 SELL / −1 BUY. m_v — истинный мид площадки
в момент филла; F̄ — depth-weighted мид всех площадок; F_0^экр — то же по мидам
снимков возрастом до 26с. Σ s·(p_f−F_0^экр)·q = колонка «заработок R»
(ledger_uc.cpp:2082–2095).

Числовой пример (BTC≈85000, 1 б.п.≈8.5 USDT, SELL q=0.05): филл 85010 о принт
90с давности, истинный мид 84990 ⇒ A=+1.0; истинный мид vs F̄=84988 ⇒ B=+0.1;
F_0=85000 vs 84988 ⇒ C=−0.6. Экран +0.5 = 1.0+0.1−0.6; реальная экономика 0.1.

Почему B мало: F_0 взвешен по глубине ⇒ у Binance (половина веса) базис почти 0;
межбиржевой базис единицы б.п., полка 3 б.п. (BTC 0.25‰+USDT 0.05‰) ⇒ базис ниже
полки ⇒ поток по шуму. «Maker-зона» = LIMIT IOC = тейкер. Резидентные заявки
(CE_BAND_MAKER_RESERVE_ENABLED) выключены. Полоса без клиентов не интернализирует.

## Арбитражёры: почему заработок скачет

Арбитражёр делает работу переводчиков второй раз: две ноги торгуют в ту же
сторону. По CE_algorithm_v2 арбитражёр — «перевозчик», внешнее действие — перевод,
рыночного риска нет. ADR-065 Q2 заменил перевод хеджем, ADR-069 разделил на две
ноги (src −f, dst +f).

Проверка на заголовках: один такт, okx дороже Binance на 5 б.п. Сумма дельт в узле
BTC@binance = −2.236 вместо 0 (W·c=0 нарушен); система покупает на дешёвой вдвое
больше; кратность 2.00.

| Агент | Узел | Дельта такта тыс.USDT | Хедж |
|---|---|---|---|
| T_BTC_binance | BTC@binance | −1.118 | покупка Binance |
| A_BTC_binanceokx src | BTC@binance | −1.118 | покупка Binance |
| T_BTC_okx | BTC@okx | +1.118 | продажа okx |
| A_BTC_binanceokx dst | BTC@okx | +1.118 | продажа okx |

Три следствия: (1) объём и дисбаланс удваиваются; (2) ноги хеджируются независимо
(своя полоса/cooldown/доля) ⇒ при исполнении одной и истечении IOC другой —
открытая позиция по цене актива; (3) экран сводит ноги: R=min(B,S)(avgS−avgB),
R+U=(B−S)P_dst+(S_not−B_not). Пример скачка: B=0.30@84990, S=0.20@85005, третья IOC
истекла ⇒ R=+3.0, R+U при P_dst=85000 = +4.0, при падении BTC до 84745 = −21.5.
Знак меняет цена, не работа арбитражёра; при разнице ног 1 BTC ход даёт ±255.

Что было бы правильно: если перевода нет, арбитражёр не должен торговать на рынке
вовсе. Его позиция = дисбаланс остатков; заработок = тариф перевоза + изменение
базиса, не цена актива. Рыночная «репликация перевода» погасила бы сделки
переводчиков (платя спред дважды) — доказательство несовместимости рыночного
хеджа обоих видов агентов с замкнутым клирингом.

## План работы с экспертом

Эксперт валидирует экономику и реалистичность, не код. Сессии по стоимости
ошибки: модель/цель → данные → исполнение → учёт → поведение → калибровка.

1. **Модель и цель.** Что считать заработком «без клиентов» (MTM?); допустим ли
   арбитраж без перевода. → целевая метрика и роль арбитражёра.
2. **Рынок и данные.** Возраст снимков/принтов, истинный базис, комиссии. →
   допуск устаревания и список площадок.
3. **Исполнение.** IOC, резидентные, очередь, задержка, комиссии. → принять
   симулятор как эталон.
4. **Учёт и экраны.** Разложение P&L, инварианты. → принять экраны.
5. **Поведение агентов.** 3–5 эпизодов. → правки логики.
6. **Калибровка.** Парето P&L vs max|позиции|. → параметры и лимиты.

Базовые документы (IN-017, Кривые, CE_algorithm_v2) — гипотезы, не эталон.
Академические работы: Barzykin–Bergault–Guéant (2023); Avellaneda–Stoikov (2008);
Budish–Cramton–Shim (2015); Makarov–Schoar (2020).

### Выжимка эксперимента (одна страница/прогон, скриптом)

Блоки: Паспорт (ID, окно, гипотеза, SHA, config_version, Δпараметров, флаги,
площадки, повторы) · Рынок в окне (σ, спред, базис медиана/p90, возраст p50/p90) ·
Итог (P&L системы MTM ±95% ДИ; A/базис/перенос/комиссии; оборот; P&L/оборот) ·
Риск (max|нетто|, max дисбаланс, max|c+in_flight|, доля тейкера, доля истёкших
IOC) · Инварианты (W·c=0; c+in_flight=I−F; ΣP&L+дом=P&L системы; сверка ledger↔VFD)
· Аномалии (5 худших филлов) · Вывод. Сводятся в журнал: дата·ID·гипотеза·
изменение·результат·решение.

### Экранные формы

- Ф1 «Система»: P&L системы и слагаемые; остатки актив×площадка; нетто; светофор
  инвариантов.
- Ф2 «Агент»: α, полка, γ, z_lim, z_mkt; c, in_flight, I, F; якорь+возраст, цена
  узла, d, F_0, сдвиг; разница ног B−S.
- Ф3 «Журнал хеджей»: от эмиссии до филла (время, сторона, объём, зона, лимит,
  мид/F_0 при эмиссии и филле, цена филла, возраст принтов, проскальзывание,
  статус, причина).
- Ф4 «Данные»: возраст снимка по площадке, разность возрастов, кажущийся vs
  синхронный базис, отброшенные кривые.
- Ф5 «Эксперименты»: реестр прогонов (ID, config_version, окно, ссылка, решение).

Диагностические параметры: возраст принта при филле (норма: все после эмиссии →
причина 1); проскальзывание тейкера к миду (норма ≤0; >0 → причина 1); разность
возрастов якорей (p90 ≤ допуска → причина 2); доля фантомного потока (≈0 → причина
2); узловой баланс Σ(I−F) (=0 → причина 3); разница ног B−S (=0); нетто по активу
(≈0); невязка c+in_flight−(I−F) (=0); насыщение сдвига |γ·b|=K (≈0); однонаправ-
ленность хеджа (<0.8); базис площадки к F_0 (среднее≈0 → структурно-убыточная);
P&L/оборот (> комиссии тейкера).

## Поэтапное устранение

Порядок: измеримость (0–1) → три главные причины (2–4, независимы) → экономика и
калибровка (5–6). Каждый этап — ворота (числовой критерий dev + сдвиг в двойнике).

- **0. Остановить калибровку, зафиксировать базу.** Профиль dev→git; история
  config_version; журнал прогонов; запись снимков/принтов с биржевым временем в
  ClickHouse (replay); генератор выжимки; быстрые проверки причин 1 и 3. Ворота:
  прогон восстанавливается по run_id; причины 1 и 3 подтверждены.
- **1. Закрытый учёт.** P&L системы = MTM; слагаемые по агентам; тесты W·c=0,
  c+in_flight=I−F, ΣP&L+дом=P&L системы. Ворота: за 24ч сумма = MTM до 0.01 USDT;
  W·c красный ровно для ног арбитражёров.
- **2. Арбитражёр без рыночного хеджа.** Флаг «не эмитит хедж»; позиция = дисбаланс;
  заработок = тариф + базис; γ_A>0; перевод — отдельной фичей. Ворота: W·c=0 каждый
  такт; объём хеджей = объёму переводчиков; нетто≈0; corr(P&L, ΔP_BTC)≈0.
- **3. Честный симулятор исполнения.** ADR-072 §B: только принты после эмиссии +
  задержка; тейкер = текущий снимок книги; maker = резидент с долей очереди π;
  комиссии; мид/F_0 на эмиссии и филле; принт один раз. Ворота: тест случайной
  стратегии P&L/оборот = −(полуспред+комиссия); проскальзывание тейкера ≤0; 0
  филлов по принту старше эмиссии.
- **4. Синхронные данные.** Биржевое время в снимках; якорь не старше допуска;
  полка c_v≥k·σ·√возраст; WebSocket/учащённый опрос. Ворота: p90 разности
  возрастов ≤ допуска; фантомный поток <10%.
- **5. Экономика «без клиентов».** ≥2 недели записанных данных: захват базиса vs
  комиссии. Ворота: P&L/оборот >0 вне выборки — либо решение не торговать.
- **6. Калибровка.** Сетка γ_s×z×K по символам (γ_s∝σ/√Λ); Парето P&L vs max|поз|.
  Число окон n≈2(1.96·σ_w/Δ)²; σ_w≈31 USDT/4мин ⇒ ~74 окна/вариант (~5ч).

### Быстрые проверки на dev (SQL)

Момент эмиссии зашит в intent_id (ce|band|агент|актив|площадка|мс).

Причина 1 (возраст принтов старше эмиссии, 24ч):
```sql
SELECT split_part(intent_id,'|',3) AS agent, count(*) AS fills,
  avg((SELECT max(split_part(intent_id,'|',6)::bigint - (t->>'exchange_ms')::bigint)
       FROM jsonb_array_elements(considered_trades) t
       WHERE (t->>'crosses')::bool AND (t->>'exchange_ms')::bigint > 0)) / 1000.0
    AS oldest_crossing_print_before_emit_s
FROM venue_fill_diagnostics
WHERE hedge_flow_id LIKE 'ce|band|%' AND filled_qty > 0
  AND created_at > now() - interval '24 hours'
GROUP BY 1 ORDER BY 2 DESC;
```

Причина 3 (одна ли сторона у T_* и A_*, BTC, по часам):
```sql
SELECT venue, date_trunc('hour', created_at) AS h,
  sum(CASE WHEN split_part(hedge_flow_id,'|',3) LIKE 'T\_%'
      THEN CASE side WHEN 'BUY' THEN filled_qty ELSE -filled_qty END END) AS net_buy_translators,
  sum(CASE WHEN split_part(hedge_flow_id,'|',3) LIKE 'A\_%'
      THEN CASE side WHEN 'BUY' THEN filled_qty ELSE -filled_qty END END) AS net_buy_arbitrageurs
FROM venue_fill_diagnostics
WHERE hedge_flow_id LIKE 'ce|band|%' AND filled_qty > 0 AND symbol LIKE 'BTC%'
GROUP BY 1, 2 ORDER BY 2 DESC, 1;
```
Одинаковые знаки двух столбцов подтверждают удвоение. У Coinbase exchange_ms=0,
первый запрос её пропускает.
